# v5.3 优化方案：诊断增强 + 信用归因修复 + Config 感知训练

> 日期：2026-04-14
> 基于：v52-step8500 checkpoint（AvgCS=1320, MinCS=871, CPS=0.895, Survival=0.818）
> 目标：降低分数方差，提高 MinCS 至 >950

---

## 一、当前状态

v5.2 训练至 step 64k，在 step 8k-12k 达峰后持续下降。最佳 checkpoint v52-step8500：
- AvgCS=1320, **MinCS=871**（差距 449，方差大）
- CPS=0.895, Survival=0.818, CS×Surv=941
- Step 12k 后 CPS/Survival/CS 全线下降，至 step 64k 无回升

**核心问题**：MinCS 远低于 AvgCS，说明模型在部分场景下发生灾难性死亡。

---

## 二、根因分析

### 2.1 奖励信用归因失败（核心问题）

这是 MinCS 低的根本原因。

| 信号 | 累积量 | GAE 传播 50 步后 | GAE 传播 100 步后 |
|------|--------|------------------|-------------------|
| 清扫 reward | +1500（~1000 格 × 1.5） | — | — |
| 碰撞死亡 penalty | -8.0（一次性） | -8.0 × 0.047 = **-0.38** | -8.0 × 0.002 = **-0.02** |
| 电池死亡 penalty | -3.0（一次性） | -3.0 × 0.047 = **-0.14** | -3.0 × 0.002 = **-0.006** |

GAE 衰减公式：γ^N × λ^N = 0.99^50 × 0.95^50 ≈ 0.047

**关键洞察**：导致死亡的关键决策（没及时充电、走向 NPC）通常发生在死亡前 100+ 步。此时 GAE 传播的死亡信号已经几乎为零（-0.02），完全无法与当步的清扫奖励（+1.5）竞争。

**结果**：模型学会了"平均清扫好"但没学会"避免灾难"。在高难度 config（低电量/多 NPC）下，这个缺陷暴露为灾难性低分 → MinCS 低。

### 2.2 诊断指标缺失

当前日志只有聚合均值，无法定位问题：

| 缺失的指标 | 为什么重要 |
|-----------|-----------|
| 各奖励分量趋势 | 不知道 cleaning 是否过于主导，NPC penalty 是否太弱 |
| 每 config 死亡率 | 不知道是哪些 (robot, charger, battery, max_step) 组合导致死亡 |
| 死亡轨迹（最后 N 步） | 不知道死亡前发生了什么（电池是否在下降？是否在返回充电？） |
| Value prediction accuracy | 不知道 V(s) 是否准确，影响 advantage 估计质量 |

### 2.3 Config 采样均匀

eval_hard 阶段所有 config 等概率采样。难 config（4 robot, 1 charger, 低电池, 2000 步）曝光不足，模型在这些场景上学习不充分。

## 三、方案设计

### Phase 1：诊断增强（零训练影响）

> 只增加可观测性，不改任何奖励数值或训练逻辑。

#### 1.1 奖励分量追踪

**文件**：`preprocessor.py`, `agent.py`, `train_workflow.py`, `monitor_builder.py`

`reward_process()` 返回 `(total_reward, components_dict)`，其中 components 包含：
- cleaning, streak, edge, explore, frontier, charger_approach
- charge, npc, revisit, stuck, idle, efficiency, urgency

每步累加到 `rolling_reward_components`，每 60 秒上报 monitor 面板。

**价值**：可以追踪哪个分量在驱动行为。如果 cleaning 占比 >80%，说明模型太贪清扫；如果 urgency 始终接近 0，说明低电量信号太弱。

#### 1.2 死亡轨迹日志

**文件**：`train_workflow.py`

保留每 episode 最近 20 步状态快照：`{step, battery, charger_slack, nearest_npc_dist, mode, action}`

死亡时输出：
```
[DEATH_TRAJ] ep:500 reason:battery traj=[s180:bat=30/200 slack=-5.2 npc=45 mode=1 act=3 | s181:bat=29/200 slack=-6.1 npc=42 mode=1 act=2 | ...]
```

**价值**：可以定位死亡原因——是充电路线被堵？是 NPC 逼近时没逃跑？是充电站太远来不及？

#### 1.3 每 config 失败率追踪

**文件**：`train_workflow.py`

按 `(robot_count, charger_count, battery_bin, max_step_bin)` 追踪死亡率。每 50 episode 输出：
```
[CONFIG_RISK] r4_c1_b200_s2000:67%(6ep) r3_c2_b120_s1500:50%(4ep)
```

**价值**：精准定位哪些 config 是 MinCS 的杀手。

#### 1.4 Monitor 面板

新增 6 个奖励分量 line chart：Cleaning, NPC Penalty, Charge, Urgency, Efficiency, Frontier。

### Phase 2：信用归因修复

#### 2.1 outcome_bonus 按剩余步数缩放

**文件**：`train_workflow.py` `_handle_episode_end()`

```python
_base_bonus = {
    "completed": 1.5, "battery": -3.0,
    "collision": -8.0, "unknown": -4.0,
}.get(fail_reason, -4.0)

if fail_reason in ("battery", "collision", "unknown"):
    steps_remaining_ratio = max(0.0, 1.0 - float(step) / max_step_actual)
    outcome_bonus = _base_bonus * (1.0 + 2.0 * steps_remaining_ratio)
else:
    outcome_bonus = _base_bonus
```

效果对比（以 battery 死亡 base=-3.0 为例）：

| 死亡时刻 | steps_remaining_ratio | 缩放因子 | 最终 bonus | GAE 50 步后有效信号 |
|----------|----------------------|----------|-----------|-------------------|
| step 100/2000 | 0.95 | 2.90 | **-8.70** | **-0.41** ← 可与 cleaning +1.5 竞争 |
| step 500/2000 | 0.75 | 2.50 | -7.50 | -0.35 |
| step 1000/2000 | 0.50 | 2.00 | -6.00 | -0.28 |
| step 1500/2000 | 0.25 | 1.50 | -4.50 | -0.21 |
| step 1900/2000 | 0.05 | 1.10 | -3.30 | -0.16 |

对比旧方案（不缩放）：step 100 死亡 bonus=-3.0 → GAE 50 步后仅 -0.14，完全无法与 +1.5 竞争。

#### 2.2 Battery hazard 信号强化

**文件**：`preprocessor.py` urgency_penalty 部分

```
旧：max -0.4/步（远小于 cleaning +1.5）
新：max -1.3/步（Level 1: -0.8 + Level 2: -0.5）
```

Level 1: charger_slack < 0 → -0.8 × severity（电量不够到充电站）
Level 2: battery < 15% 且 charger_slack 0-10 → -0.5 × severity（在返回途中但电量极低）

**价值**：低电量时的即时信号接近 cleaning reward 量级，模型每步都能收到"应该去充电"的强信号，而非只依赖 100 步后微弱的 GAE 传播。

#### 2.3 NPC 近距离持续惩罚

**文件**：`preprocessor.py`

NPC 距离 < 3 时额外 -0.6 × (3-dist)/3 每步持续惩罚。

#### 2.4 clip 范围 [-5, 5] → [-6, 6]

强化后总奖励可能超出旧范围。

---

### Phase 3：Config 感知训练

#### 3.1 超采样高死亡 config

**文件**：`train_workflow.py` EnvConfigSampler

- 利用 Phase 1.3 的 config_stats 数据
- eval_hard 阶段：50% 概率强制采样高死亡 config（在 config 参数附近扰动）
- 每 100 episode 同步死亡率到 sampler

**价值**：难 config 的曝光频率提升 3-5×，模型有更多机会学习如何处理这些场景。

## 四、实施顺序

```
Phase 1（诊断增强）
  ├── 1.1 奖励分量追踪
  ├── 1.2 死亡轨迹日志
  ├── 1.3 每 config 失败率追踪
  └── 1.4 Monitor 面板
       ↓ 部署后 resume 训练 ~500 episode 收集基线数据

Phase 2（信用归因修复）
  ├── 2.1 outcome_bonus 缩放
  ├── 2.2 battery hazard 强化
  ├── 2.3 NPC proximity penalty
  └── 2.4 clip 范围调整
       ↓ 基于 Phase 1 基线数据，重新 resume 训练

Phase 3（Config 感知训练）
  ├── 3.1 超采样高死亡 config
  └── 3.2 动态同步死亡率
       ↓ 在 Phase 2 运行中自动生效
```
