## 一、项目概况

RL训练系统（PPO + KaiwuDRL框架），为腾讯Arena"扫地机器人"竞赛训练模型。
从Windows/Kaiwu平台迁移到Linux独立运行（Docker Compose）。

**服务器资源**：4×A10 GPU (23028 MiB each), 118 CPU cores, 503GB RAM

**当前性能**：~3.5-6.4 steps/s（受配置影响波动大），GPU0 利用率 16-30%，GPU1-3 0%。

## 二、已完成的工作

### 2.1 三轮速度实验（T1-T3）

| Test | 配置 | steps/s | data_fetch_avg | real_train_avg | samples/s |
|------|------|---------|---------------|----------------|-----------|
| T1 | 8gc, batch=2048, Uniform, dump=100 | 7.09 | 185.6ms (80%) | 44.4ms | 14,528 |
| T2 | 8gc, batch=4096, Fifo, dump=100* | 7.02 | 114.2ms | 44.3ms | 28,741 |
| T3 | 16gc, batch=4096, Fifo, dump=100* | 6.43 | 133ms | 41ms | 28,023 |

\* dump_model_freq=500 已写入配置文件，但因patch时序问题未生效，实际仍为100

**关键结论**：
- **加环境没用**：T2→T3 几乎无提升甚至略降
- **win参数有效**：T1→T2 samples/s翻倍（batch=4096），但steps/s未提升
- **瓶颈确认**：data_fetch（等待reverb数据）占训练时间74-85%

### 2.2 瓶颈根因分析

1. **Reverb TCP数据管道是核心瓶颈**：aisrv → TCP/gRPC → reverb_server → TCP/gRPC → learner，序列化/反序列化开销大
2. **dump_model_freq=100过于频繁**：每~15s一次on-policy重置（清空buffer+推送模型+等待aisrv确认），加剧data_fetch等待
3. **样本产出过剩35:1**：16 gamecore产出~969K samples/s，learner消费~28K samples/s，过剩样本被丢弃
4. **多GPU完全闲置**：框架不支持多learner分布式训练

### 3.2 关键Bug：post_init_patch时序问题

**问题**：docker-compose command 中 `start_train_client.sh learner & sleep 10 && post_init_patch.py` 有竞争条件。
- 如果 learner 在10s内加载 CONFIG → CONFIG读的是init_code.sh复制的源文件（正确）
- 如果 learner 在10s后才加载 CONFIG → CONFIG读的是post_init_patch修改后的文件

**影响**：源文件已有正确值，但post_init_patch会用env var覆盖（可能导致格式问题，如Fifo vs reverb.selectors.Fifo）

**建议**：统一env var值使用完整格式（已完成reverb_sampler修复），或改为pre-init patching。

## 四、下一步优化方案（按优先级）

### P0: 确认当前配置生效 + 收集baseline

等容器运行5分钟后收集metrics，确认：
- dump_model_freq=500生效
- reverb_sampler正确（Fifo）
- steps/s回到~6-7范围

### P1: 切换 replay_buffer_type 到 zmq（最大预期收益）

**原理**：消除TCP/gRPC序列化开销，使用共享内存零拷贝传输

```
当前 reverb:  aisrv → TCP/gRPC → reverb_server → TCP/gRPC → learner
ZMQ 方案:     aisrv → 共享内存 → learner (后台预取线程)
```

**框架已支持**：
- `configure.toml:260`: `replay_buffer_type = "reverb"` → 改为 `"zmq"`
- `replay_buffer_wrapper.py:83`: ZMQ 分支已实现
- `zmq_replay_buffer.py`: 零拷贝+后台预取+双缓冲队列

**实施步骤**：
1. 在 `post_init_patch.py` 中新增 `replace_toml_key(learner_conf, 'replay_buffer_type', 'KAIWU_EXPERIMENT_REPLAY_BUFFER_TYPE')`
2. `.env` 中新增 `KAIWU_EXPERIMENT_REPLAY_BUFFER_TYPE=zmq`
3. 重启观察 learner log
4. **风险**：需验证 on-policy 的 model_version 样本过滤在 ZMQ 方案下正常

**预期**：如果兼容，steps/s 提升到 ~15-20

### P2: 微调参数

| 参数 | 当前值 | 建议值 | 预期效果 |
|------|--------|--------|----------|
| predict_batch_size | 32 | 64-128 | 减少通信开销 |
| sample_data_return_data_type | "numpy" | "tensor" | 消除numpy→tensor转换 |
| torch_num_threads | 1 | 2 | 加速CPU预处理 |

### P3: 多GPU利用（框架限制）

框架不支持多learner分布式训练。可行但需要改造的方案：
- 多learner各训练独立模型（中难度）
- 业务层 torch.compile（低难度，10-30% real_train加速）
