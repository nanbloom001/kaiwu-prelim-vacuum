## 一、项目概况

RL训练系统（PPO + KaiwuDRL框架），为腾讯Arena"扫地机器人"竞赛训练模型。
从Windows/Kaiwu平台迁移到Linux独立运行（Docker Compose）。

**服务器资源**：4×A10 GPU (23028 MiB each), 118 CPU cores, 503GB RAM

**当前性能**：~3.5-6.4 steps/s（受配置影响波动大），GPU0 利用率 16-30%，GPU1-3 0%。

## 2026-04-14 最新进展

### E. AMP 混合精度训练已启用（+24% steps/s）

**变更**：
1. `train/.docker-compose.yaml` learner environment 添加 `KAIWU_SERVICE_NAME: learner`（触发 AMP + 优化的 torch 线程设置）
2. `code/agent_ppo/agent.py:220-232` 修复 `fused` 和 `foreach` 优化器标志冲突（PyTorch Adam 不允许两者同时为 True）

**5 分钟基准对比**：

| 指标 | ZMQ FP32 基线 | ZMQ + AMP | 变化 |
|------|---------------|-----------|------|
| steps/s | 23.0 | **28.5** | **+24%** |
| real_train | 32.2 ms | 26.5 ms | -18% |
| data_fetch | 11.3 ms | 7.0 ms | -38% |
| total cost | 43.5 ms | 33.5 ms | -23% |
| 错误 | 0 | 0 | — |

**根因分析**：
- 之前 `KAIWU_SERVICE_NAME` 未设置 → `service_name=""` → `"learner" in ""` = False → AMP 被跳过
- 同时 `_configure_torch_runtime` 将 aisrv 的线程设为 1，但 learner 因 service_name="" 也走了默认路径
- 现在设为 `learner` 后，AMP 启用（autocast + GradScaler + fused Adam），线程设为 4/2（CPU 端加速 data_fetch）
- fused Adam 比 foreach 更快（单 kernel 融合），且与 AMP 兼容

**已验证**：`use_amp: true`（runtime_probe 确认），15000+ steps 无错误，checkpoint 正常保存。

**下一步优化方向**（按优先级）：
1. **torch.compile**：对 model.forward + loss 做 JIT 编译，预计再降 15-25% real_train
2. **多 learner 实验性部署**：利用 GPU2/3 训练独立模型，增加总训练吞吐
3. **batch size 调优**：4096 → 8192 试探 data_fetch 与 real_train 的平衡点
4. **预取优化**：ZMQ 双缓冲队列深度调优

### B. 已确认并修复的关键问题：aisrv GPU 路由失效

旧逻辑依赖 aisrv 容器的 hostname 后缀解析副本编号，但容器内 `/etc/hostname` 实际是随机容器 ID，不是 `kaiwu-train-aisrv-1/2`。结果是两路 aisrv 都没有导出正确的 `CUDA_VISIBLE_DEVICES`，运行时虽然都显示 `cuda:0`，但实际上是“4 卡全部可见时的本地 0 号卡”。

修复方式：

- 新增 `code/agent_ppo/utils/container_routing.py`
- 由 compose 在 aisrv 启动前调用该 helper
- helper 用“当前容器 IP”去匹配 `kaiwu-train-aisrv-1/2` 的 service DNS IP，得到稳定的 `aisrv_index`
- 再按 `KAIWU_AISRV_GPU1_NUM` / `KAIWU_AISRV_GPU2_NUM` 把 index 映射到目标物理 GPU

已验证结果：

- aisrv-1 banner：`aisrv_index=1 target_gpu=1 cuda_visible_devices=1`
- aisrv-2 banner：`aisrv_index=2 target_gpu=2 cuda_visible_devices=2`
- learner `runtime_probe` 已显示：
	- `CUDA_VISIBLE_DEVICES = 0`
	- `torch_cuda_device_count = 1`
	- `requested_device`、`algorithm_device`、`model_param_device` 均为 `cuda:0`
	- `replay_buffer_type = reverb`
- 两路 aisrv 的 `runtime_probe` 均显示：
	- `CUDA_VISIBLE_DEVICES` 与 `NVIDIA_VISIBLE_DEVICES` 已分别变为 `1` / `2`
	- `torch_cuda_device_count = 1`
	- `requested_device`、`model_param_device`、输入张量 device 仍是本地 `cuda:0`

这说明 GPU 路由现已正确：每个 aisrv 只看到自己绑定的一张物理卡，并在容器内继续使用本地 `cuda:0` 语义。

### 2.1 三轮速度实验（T1-T3）

| Test | 配置 | steps/s | data_fetch_avg | real_train_avg | samples/s |
|------|------|---------|---------------|----------------|-----------|
| T1 | 8gc, batch=2048, Uniform, dump=100 | 7.09 | 185.6ms (80%) | 44.4ms | 14,528 |
| T2 | 8gc, batch=4096, Fifo, dump=100* | 7.02 | 114.2ms | 44.3ms | 28,741 |
| T3 | 16gc, batch=4096, Fifo, dump=100* | 6.43 | 133ms | 41ms | 28,023 |

\* dump_model_freq=500 已写入配置文件，但因patch时序问题未生效，实际仍为100

**关键结论**：
- **加环境没用**：T2→T3 几乎无提升甚至略降
- **win参数有效**：T1→T2 samples/s翻倍（batch=4096），但steps/s未提升
- **瓶颈确认**：data_fetch（等待reverb数据）占训练时间74-85%

### 2.2 瓶颈根因分析

1. **Reverb TCP数据管道是核心瓶颈**：aisrv → TCP/gRPC → reverb_server → TCP/gRPC → learner，序列化/反序列化开销大
2. **dump_model_freq=100过于频繁**：每~15s一次on-policy重置（清空buffer+推送模型+等待aisrv确认），加剧data_fetch等待
3. **样本产出过剩35:1**：16 gamecore产出~969K samples/s，learner消费~28K samples/s，过剩样本被丢弃
4. **多GPU完全闲置**：框架不支持多learner分布式训练

## 四、下一步优化方案（按优先级）

### P0: 确认当前配置生效 + 收集baseline

等容器运行5分钟后收集metrics，确认：
- dump_model_freq=500生效
- reverb_sampler正确（Fifo）
- steps/s回到~6-7范围

### P1: 修复 learner 端 ZMQ 的 CUDA/fork 兼容性（当前 blocker）

当前已经验证：ZMQ 路径能够被正确激活，但 learner 会在创建 agent wrapper 时因为 fork 后重入 CUDA 而失败。因此，P1 不再是“直接切 ZMQ”，而是先修复 ZMQ 在 learner 端的进程模型兼容性。

**现象**：

- ZMQ 已生效：`learner train replay_buff, use zmq`
- 真实失败点：`Cannot re-initialize CUDA in forked subprocess`

**根因方向**：

- learner 的某个子进程路径在 CUDA 已经触发 lazy init 后又走了 fork
- 或者 agent / model 的 CUDA 初始化发生得早于 ZMQ 路径所需的多进程启动

**修复后仍值得做 ZMQ 的原因**：消除 TCP/gRPC 序列化开销，使用共享内存零拷贝传输

```
当前 reverb:  aisrv → TCP/gRPC → reverb_server → TCP/gRPC → learner
ZMQ 方案:     aisrv → 共享内存 → learner (后台预取线程)
```

**框架已支持**：
- `configure.toml:260`: `replay_buffer_type = "reverb"` → 改为 `"zmq"`
- `replay_buffer_wrapper.py:83`: ZMQ 分支已实现
- `zmq_replay_buffer.py`: 零拷贝+后台预取+双缓冲队列

**下一步实施方向**：

1. 确认 ZMQ 模式下 learner 是在哪个具体进程路径里 fork 了已触发 CUDA 的父进程
2. 优先评估两类修复：
	- 将该路径改为 `spawn`
	- 或把 agent/model 的 CUDA 初始化下沉到子进程内部，避免父进程先触发 CUDA
3. 修复后重新做同一套 smoke test：
	- learner / aisrv 存活
	- learner 持续产出 `train once cost time`
	- 对比 `data_fetch` 是否显著下降
4. **额外风险**：即便修掉 CUDA/fork 问题，仍需验证 on-policy 的 model_version 样本过滤在 ZMQ 路径下是否正常

**预期**：只有在上述兼容性问题修复后，ZMQ 才有资格进入性能对比阶段
