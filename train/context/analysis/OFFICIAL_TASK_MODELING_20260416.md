## 1. 一句话定义赛题

这道题不是普通的“扫地积分题”，而是一个：

- **有限时域**
- **资源受限**
- **局部地图可观、全局实体部分可观**
- **带竞争、带硬失败条件**
- **多时间尺度耦合**

的区域覆盖决策问题。

更直白地说，它要求机器人同时处理四件事：

1. 局部合法移动与避障
2. 高效覆盖与减少重复路径
3. 在官方机器人竞争下尽快吃掉有价值区域
4. 在电量耗尽前正确回充，并重复多轮清扫-回充循环

这四件事里，前两件偏“局部控制”，后两件偏“长期规划”，它们不是一个难度层级的问题。

## 2. 官方规则中的固定不变量

以下是从官方文档直接抽出来、在所有训练/评估中都成立的核心规则。

### 2.1 地图与坐标

- 地图大小固定为 `128×128`
- 坐标系：左上角 `(0, 0)`，`x` 向右正，`z` 向下正
- 地图被栅格化
- 道路区域连通，不存在孤立可达区域

这意味着：

- 全局空间足够大，无法依靠局部视野直接覆盖全图
- 拓扑结构是静态的，但初始可见信息不完整

### 2.2 小悟机器人（玩家机器人）

- 数量固定为 `1`
- 动作空间固定为 `8` 个方向
- 每步移动 `1` 格
- 每走一步消耗 `1` 电量
- 经过污渍格自动完成清扫
- 进入充电桩 `3×3` 范围即瞬时充满

### 2.3 官方机器人（NPC）

- 官方机器人数量在配置范围内变化，但行为规则固定
- 每个官方机器人围绕出生点在 `21×21` 区域内随机移动
- 官方机器人经过污渍也会把污渍清掉
- 小悟机器人进入官方机器人中心 `3×3` 范围就算碰撞，任务立即失败

这里要特别注意两点：

- 官方机器人既是**危险源**，也是**竞争者**
- 它们不仅会撞死你，还会提前清掉本来你可以拿分的污渍

### 2.4 充电桩

- 每个充电桩占 `3×3`
- 进入范围即瞬时充满
- 充电动作没有额外时间成本，但“到达充电桩”本身有路径成本

这意味着充电问题的关键不是“站上去充多久”，而是：

- 什么时候该转入回充
- 还能不能及时走到桩上

### 2.5 终止条件

任务只会以三种方式结束：

- `completed`
  - 达到 `max_step`
- `failed`
  - `battery <= 0`
- `failed`
  - 进入官方机器人 `3×3` 范围

这里最关键的建模含义是：

- **电池耗尽和碰撞都是硬失败**
- 只要失败，后面所有潜在清扫收益都全部丢失

### 2.6 计分规则

任务得分 = 小悟机器人自己清扫的污渍格数

官方机器人清掉的格子：

- 不给玩家得分
- 玩家之后再经过也不会补分

这使得赛题不只是“覆盖更多面积”，而是“在时间窗口内优先拿下会被别人抢走的面积”。

## 3. 官方可手动配置的环境轴

官方文档明确给出了 6 个训练期可配环境参数。这些参数共同定义了“环境分布”，不是简单调难度的几个按钮。

### 3.1 可配置项总表

| 配置项 | 范围 | 默认值 | 含义 |
|---|---:|---:|---|
| `map` | `[1..10]` 的列表 | `[1..10]` | 训练使用哪些公开地图 |
| `map_random` | `true/false` | `false` | 每局随机抽地图还是顺序轮转 |
| `robot_count` | `1..4` | `4` | 官方机器人数量 |
| `charger_count` | `1..4` | `4` | 充电桩数量 |
| `max_step` | `1..2000` | `1000` | 单局最大步数 |
| `battery_max` | `100..999` | `200` | 满电电量上限 |

评估任务里也可以配置：

- 地图选择（公开地图 1-10，多选）
- `robot_count`
- `charger_count`
- `max_step`
- `battery_max`

需要特别记住一条官方约束：

- **训练配置只在训练任务里生效**
- **评估配置是单独指定的**

所以从建模角度，这道题天然存在“训练分布”和“评估分布”两个层面，泛化问题是赛题内生的，不是附加题。

### 3.2 每个配置项到底在改变什么

| 配置项 | 它改变的是什么 | 更深一层的建模含义 |
|---|---|---|
| `map` | 地形拓扑、障碍物布局、局部通道结构、出生点和充电桩候选点的几何关系 | 任务不是纯参数化问题，而是带明显空间结构变化的问题 |
| `map_random` | 训练时 episode 序列的相关性、模型是否容易记住固定地图顺序、curriculum 是否更平稳还是更抖动 | `map_random = false` 更容易让 agent 在短期内适应单一地图模式；`map_random = true` 更接近真实泛化训练 |
| `robot_count` | 安全压力和竞争压力同时变化。前者体现在高风险区域数量增加、碰撞几率上升；后者体现在官方机器人抢走污渍的速度变快、玩家的“可得分窗口”变短 | `robot_count` 不是单纯“更容易碰撞”，它也改变了价值密度随时间的衰减速度 |
| `charger_count` | 回充目标数量、平均回充路径长度、低电时的容错空间 | `charger_count` 少的时候，问题不只是“更远”，而是回充触发必须更早，局部贪心清扫更容易直接把整局送掉 |
| `max_step` | 一局允许持续多久、是否需要经历多轮清扫-回充循环、长期规划的重要性有多高 | `max_step` 很短时更像“一次性局部覆盖”；`max_step` 很长时更像“多次往返的持续收益最大化” |
| `battery_max` | 每次满电的可达范围、回充时机窗口宽度、错误容忍度 | `battery_max` 高时，模型可以靠更粗糙的回充策略也活下来；`battery_max` 低时，回充 timing 立刻变成主问题 |

## 4. 赛题的六个观察视角

为了建立“立体模型”，我建议从六个视角同时看这道题。

### 4.1 空间拓扑视角

这是一个静态大地图上的区域覆盖问题。

关键特征：

- 地图大：`128×128`
- 可达区域连通
- 障碍物塑造瓶颈、窄通道、局部死角
- 斜向移动还受“防穿角”约束

因此，地图不只是背景，而是直接决定：

- 局部动作是否有效
- 从当前位置到充电桩的真实可达代价
- 清扫路径是否容易重复绕圈

### 4.2 资源预算视角

从资源角度，这道题本质上是：

- 每步花 `1` 电
- 回到充电桩可瞬时续命
- 在有限 `max_step` 内把电量转化为尽可能多的有效清扫得分

这等价于：

- 电量是一种“可转换为位移和得分的预算”
- 充电桩是预算重置点
- 回充路径是预算再投资的固定成本

因此清扫策略不能只看“这一步能不能加 1 分”，还要看：

- 这 1 分是不是在透支下一轮清扫机会

### 4.3 竞争博弈视角

虽然这不是显式对抗游戏，但官方机器人形成了弱对抗环境。

它们带来两类竞争：

1. **地盘竞争**
   - 你还没扫到的污渍，NPC 可能先扫掉
2. **时机竞争**
   - 你绕路、卡住、回充过慢时，机会成本在持续上升

因此“污渍”不是静态奖励，而是：

- 一个会被时间和 NPC 共同蚕食的机会集合

### 4.4 安全约束视角

安全约束有两层：

1. 短时安全
   - 本步/下几步是否会进入 NPC `3×3` 危险区
2. 长时安全
   - 现在继续扫会不会导致未来来不及回桩

前者偏局部反应；后者偏长期规划。  
这两类安全虽然都叫“安全”，但本质完全不同。

### 4.5 信息结构视角

官方协议里，信息并不是完全局部的，也不是完全全局的，而是“混合可观测”。

#### 已知/全局可得的信息

- 自己的全局绝对坐标
- 自己当前电量、分数、已清扫数
- 所有官方机器人当前全局绝对坐标
- 所有充电桩全局绝对坐标和尺寸
- 当前环境配置，如 `npc_count`、`total_charger`、`battery_max`、`max_step`

#### 仅局部可见的信息

- `21×21` 视野内的地图状态：
  - 障碍
  - 已清扫
  - 污渍

#### 隐藏/需要记忆和推断的信息

- 视野外的地图几何细节
- 视野外哪些道路还脏、哪些已经被自己或 NPC 扫过
- 未来若干步 NPC 会怎么走
- 当前是否已经进入“必须回充”的阶段

因此，这个任务不是纯 POMDP，也不是纯 fully observed MDP，而是：

- **动态实体信息全局可见**
- **静态地图清扫状态局部可见**

这点非常重要。  
它意味着：

- 充电桩和 NPC 的“位置不知道”不是主问题
- 真正难的是“地图覆盖状态不知道”和“长期阶段状态不显式”

### 4.6 分布与泛化视角

官方赛题天然包含分布转移：

- 训练可用公开地图 1-10
- 最终测评有 5 张隐藏地图

也就是说，真正想拿比赛成绩，模型需要的不只是：

- 在固定公开图上学会路径

而是：

- 学会一类“地图上如何覆盖、何时回充、如何避险”的策略模板

这也是为什么 `map` 和 `map_random` 不能只看成数据加载选项，它们直接决定模型是学策略还是记地图。

## 5. 形式化任务模型

### 5.0 形式化对象速览

| 对象 | 当前赛题里的含义 | 建模重点 |
|---|---|---|
| `state` | 地图拓扑、污渍分布、己方位置/电量、NPC 位置、充电桩位置、剩余步数 | 环境真实完整状态 |
| `observation` | 局部地图、全局实体、环境统计 | agent 实际可用信息 |
| `action` | 8 方向移动 | 非法移动和穿角失败有真实代价 |
| `objective` | 最大化玩家自己清扫到的污渍格数 | 官方最终目标 |
| `failure` | battery / collision | 硬失败导致后续潜在收益清零 |

### 5.1 状态

如果写成强化学习语言，完整环境状态至少包含：

- 静态地图拓扑
- 当前污渍分布
- 小悟位置
- 小悟电量
- 官方机器人位置
- 充电桩位置
- 剩余步数

但 agent 实际拿到的是观测而不是完整状态。

### 5.2 观测

每一步能拿到：

- `step_no`
- `frame_state`
  - hero
  - npcs
  - organs
- `env_info`
- `map_info`（`21×21` 局部）
- `legal_act`

因此当前 RL 问题可被视为：

- 一个带全局实体表征、局部地图观测和内部记忆需求的决策问题

### 5.3 动作

动作空间固定为 8 方向。

重要的不是动作数，而是转移规则：

- 直线移动：目标格可通行即可
- 斜向移动：目标格可通行，且相邻两条边至少一条可通行
- 如果不能移动，则原地停留
- 即使原地停留，仍然消耗 1 步和 1 电量

这个规则的建模含义很强：

- “非法移动”不是零成本
- 卡墙、穿角失败、局部震荡都会直接消耗生存预算

### 5.4 奖励与目标

官方环境直接给出的 `env_reward.reward` 更接近“当前得分/表现指标”，不是你训练里必须使用的最终 shaped reward。

赛题真实目标是：

- 最大化自己清扫的污渍数量

但从策略角度，它可以拆成：

- 直接收益：当前清扫到新污渍
- 间接收益：通过回充延长生存、从而获得未来更多清扫机会
- 机会损失：被 NPC 抢先清掉的污渍
- 崩盘损失：碰撞或电量耗尽导致后续所有潜在收益清零

### 5.5 终局代价

任务失败的代价不只是“少一次奖励”，而是：

- 后续整条轨迹都没了

这使得 battery/collision 的价值传播天然是长程的。

## 6. 从配置项推导出的难度轴

### 6.0 难度轴总表

| 难度轴 | 主要由哪些配置决定 | 本质上在考什么 |
|---|---|---|
| 地图泛化轴 | `map`, `map_random` | 是学结构还是记地图 |
| 风险竞争轴 | `robot_count` | 短时安全和机会流失 |
| 回充稀缺轴 | `charger_count` | 回充路径长度和容错 |
| 生存压力轴 | `battery_max` | 回充窗口宽度和错误容忍度 |
| 长期规划轴 | `max_step`, `battery_max` | 是否必须经历多轮清扫-回充循环 |

为了把环境配置真正变成“可分析的任务空间”，我建议定义 5 条核心难度轴。

### 6.1 地图泛化轴

由以下项控制：

- `map`
- `map_random`
- 是否公开图 / 隐藏图

含义：

- 单图、固定顺序：最容易诱发记图
- 多图、随机：更接近真实泛化
- 隐藏图：检验策略模板而不是路径背诵

### 6.2 风险竞争轴

主要由 `robot_count` 控制。

含义：

- `robot_count` 越高
  - collision 风险越高
  - 可得分污渍消失越快
  - 局部安全路线选择更难

### 6.3 回充稀缺轴

主要由 `charger_count` 控制。

含义：

- charger 越少
  - 平均回充路程越长
  - 回充触发必须越早
  - 清扫和回充之间的冲突越明显

### 6.4 生存压力轴

由 `battery_max` 控制，但要和地图、charger 一起理解。

一个更有意义的量是：

- **局部生存裕量**
  - 当前电量与到最近充电桩真实路径代价之差

配置层面上：

- `battery_max` 越低
  - 对错误路径、卡墙、绕路的容忍度越低

### 6.5 长周期规划轴

由 `max_step` 与 `battery_max` 的组合共同决定。

一个直观指标是：

- `max_step / battery_max`

它表示：

- 理论上，一局是否必然要求多轮回充
- 回充策略在整局表现中的权重有多大

例如：

- `max_step = 1000`, `battery_max = 200`
  - 单靠一管电不可能撑完整局
  - 回充不是边缘能力，而是主能力

## 7. 典型场景族

### 7.0 场景族总表

| 场景族 | 典型配置特征 | 主问题 |
|---|---|---|
| 低压探索型 | 低 `robot_count`，高 `charger_count`，高 `battery_max` | 覆盖效率和少绕路 |
| 碰撞风险型 | 高 `robot_count`，局部拥挤 | 局部安全控制 |
| 回充时机型 | 少 `charger_count`，中低 `battery_max`，长 `max_step` | 何时开始回充 |
| 长局耐久型 | 长 `max_step`，需要多轮循环 | 长期收益最大化 |
| 泛化检验型 | 多图训练，隐藏图评估 | 学规则而不是背路径 |

基于官方可配轴，可以把环境划成几类典型场景。

### 7.1 低压探索型

特征：

- `robot_count` 低
- `charger_count` 高
- `battery_max` 高
- `max_step` 中等

主问题：

- 路径覆盖效率
- 减少重复访问

### 7.2 碰撞风险型

特征：

- `robot_count` 高
- 地图局部空间拥挤

主问题：

- 局部安全动作
- 通过局部风险图避开 NPC 活动带

### 7.3 回充时机型

特征：

- `charger_count` 少
- `battery_max` 低或中等
- `max_step` 长

主问题：

- 不是“能不能找到桩”
- 而是“什么时候必须切回充”

这是你们当前实验里最典型的主瓶颈场景。

### 7.4 长局耐久型

特征：

- `max_step` 很长
- 需要多轮回充
- NPC 持续清扫导致机会不断流失

主问题：

- 如何在多轮清扫-回充循环中保持长期收益最大化

### 7.5 泛化检验型

特征：

- 多图训练
- 隐藏图评估

主问题：

- 是否学到了空间策略模板，而不是固定地图路径

## 8. 当前仓库里的训练/评估空间，如何映射到官方赛题

从仓库当前实现看，你们实际上已经在围绕官方这 6 个配置轴构建更丰富的训练分布。

### 8.1 当前训练默认基线

`code/agent_ppo/conf/train_env_conf.toml` 当前基线大致是：

- `map = [1..10]`
- `map_random = true`
- `robot_count = 1`
- `charger_count = 4`
- `max_step = 1000`
- `battery_max = 300`

这说明当前主训练基线本身已经不是官方默认值，而是：

- 更偏“让 agent 先学会回充和探索”的温和版本

### 8.2 当前课程采样

`train_workflow.py` 里的 `EnvConfigSampler` 又在官方可配轴上继续扩展：

- `robot_count: 1..4`
- `charger_count: 1..4`
- `max_step: 500..2000`
- `battery_max: 120..720`
- `map`: 子集抽样
- `map_random = true`

也就是说，你们当前系统已经把官方规则空间转换成了一个更宽的训练分布。

这件事的建模含义是：

- 你们不是在训练“固定环境上的最优策略”
- 而是在训练“跨配置分布的鲁棒策略”

因此当前主瓶颈一旦表现为 `battery / return timing`，它就不是某个固定图的小问题，而是整个配置空间上都存在的结构性问题。

### 8.3 当前 benchmark 切片

当前 benchmark 典型切片包括：

- `4 chargers / 3 robots / 1000 steps / 200 battery`
- `3 chargers / 4 robots / 1200 steps / 300 battery`
- `2 chargers / 4 robots / 1600 steps / 200 battery`
- `2 chargers / 4 robots / 2000 steps / 200 battery`

这些切片正好把官方配置轴的几个关键高压组合测出来：

- 少 charger
- 多 robots
- 长 max_step
- 中低 battery

这也是为什么最近统一 eval 里，battery 问题会被稳定放大出来。

## 9. 从赛题建模反推出的核心子问题

### 9.0 子问题总表

| 子问题 | 时间尺度 | 主要输入 | 现在最容易出的问题 |
|---|---|---|---|
| 短时安全控制 | 1-5 步 | NPC 位置、局部可通行性、动作合法性 | 进入 NPC 危险区、局部误判 |
| 中时覆盖规划 | 10-60 步 | 局部污渍、访问记忆、区域价值 | revisit、orbiting、低效率 |
| 长时回充调度 | 50-200 步 | 电量、回桩代价、局部机会、剩余步数 | 回充太晚、来不及到桩 |
| 跨地图泛化 | 跨 episode | 多图结构共性 | 记图而不是学结构 |

如果把整道题拆开，它至少包含以下 4 个耦合子问题。

### 9.1 短时安全控制

目标：

- 避免在接下来 1 到 5 步内进入 NPC `3×3` 危险区

输入主要依赖：

- 当前 NPC 全局位置
- 局部地图可通行性
- 当前动作合法性

### 9.2 中时覆盖规划

目标：

- 在局部和区域尺度上提高每步得分效率
- 避免重复覆盖
- 尽快进入仍有高收益的区域

输入主要依赖：

- 局部污渍分布
- 已探索/已访问记忆
- 官方机器人对价值区的侵蚀速度

### 9.3 长时回充调度

目标：

- 决定何时从“继续扫”切到“必须回”

这是当前最关键的结构性子问题。

它依赖的不是单一数值，而是一个联合判断：

- 当前电量
- 到充电桩的真实路径代价
- 当前局部清扫机会值
- 剩余步数
- 再拖延几步后是否会穿越安全边界

### 9.4 跨地图泛化

目标：

- 在未见地图上仍能做出合理覆盖和回充决策

这要求模型学到的是：

- 规则和结构

而不是：

- 地图编号到路径模板的记忆

## 10. 这道题真正难在哪里

### 10.0 核心难点总表

| 难点 | 为什么难 | 直接后果 |
|---|---|---|
| 即时收益 vs 长期生存 | 清扫奖励密集，回充价值延迟 | 容易学成贪心清扫 |
| 局部地图可观、实体全局可观 | 需要把局部观察拼成长期覆盖状态 | 必须依赖记忆和状态摘要 |
| 竞争让价值时变 | NPC 会持续抢走潜在得分 | 同一路径在不同时间价值不同 |
| 错误动作有真实成本 | 卡墙/穿角失败也消耗步数和电量 | 安全边际被悄悄侵蚀 |

基于官方文档和当前实验，我认为这道题最难的不是“8 方向怎么走”，而是下面这几个组合难点。

### 10.1 即时收益和长期生存冲突

清扫是即时、密集、正反馈；
回充是延迟、长期、为了避免未来崩盘。

这使模型天然更容易被“再多扫几格”吸引。

### 10.2 地图局部可观，实体全局可观

NPC 和 charger 的位置是全局的，但污渍和障碍细节是局部逐步揭示的。

因此 agent 需要：

- 记住自己见过什么
- 用记忆把局部观测拼成全局覆盖图

### 10.3 竞争会让奖励时效性变化

污渍不是静态资产：

- 你不去，NPC 会去
- 你绕路，价值就可能被吃掉

这意味着“价值”本身是时变的。

### 10.4 错误动作有真实成本

卡墙、穿角失败、局部震荡：

- 不只是浪费一步
- 而是同时浪费一步和一格电

这会直接侵蚀回充安全边际。

## 11. 建模结论

### 11.0 建模结论总表

| 结论 | 含义 |
|---|---|
| 主难点不在动作空间 | 8 方向本身不是瓶颈，阶段切换才是 |
| 配置项定义的是任务族 | `robot_count/changer_count/max_step/battery_max` 共同决定难度结构 |
| 充电问题是资源调度问题 | 不是简单“看见充电桩就去” |
| 官方机器人兼具风险和竞争属性 | 既会撞死你，也会抢走得分机会 |
| 隐藏地图要求学结构 | 必须追求跨图稳定策略，而不是地图记忆 |

从官方文档出发，我会把赛题最终概括为：

> 一个在大静态拓扑地图上运行的、局部地图可观但动态实体全局可观的、带资源约束和竞争衰减的区域覆盖任务。  
> 其核心不是“找到污渍就去扫”，而是在 `清扫收益 / 回充时机 / 短时避险 / 跨图泛化` 之间做多时间尺度协调。

更进一步，若只保留对后续算法设计最关键的结论，那就是：

1. 这道题的主难点不在动作空间，而在阶段切换  
2. `robot_count / charger_count / max_step / battery_max` 不是普通参数，而是定义任务族的难度轴  
3. 充电问题本质上是长期资源调度问题，不是简单导航问题  
4. 官方机器人既是碰撞风险源，也是得分机会的侵蚀者  
5. 最终测评的隐藏地图要求模型学结构，不是背地图

## 13. 合理的评价指标设计

赛题建模清楚之后，下一步必须把“怎么判断模型变好了”也定清楚。否则会反复出现下面这些问题：

- 训练 reward 上升，但真实表现没变好
- clean score 高了，但其实是靠吃简单局、丢 hard case 换来的
- 存活率变高了，但只是保守不扫了
- CPS 看起来高了，但只是因为早死分母变小

因此评价指标必须满足 4 个原则：

1. **尽量贴近官方目标**
   - 最终目标仍是玩家机器人自己清到多少格
2. **能反映硬失败代价**
   - battery / collision 不能被平均数掩盖
3. **能区分“会扫”和“能活着持续扫”**
4. **尽量用客观可复现的量**
   - 优先使用环境日志和 benchmark 结果中可直接计算的指标

我建议把指标分成三层：

- `正式主指标`
- `分解型客观指标`
- `训练判读辅助指标`

### 13.1 正式主指标

这些指标应该用于：

- checkpoint 横向比较
- benchmark 报告
- 版本回归判断
- 重要实验结论

| 指标 | 定义 | 推荐公式 | 意义 | 备注 |
|---|---|---|---|---|
| `AvgCleanScore` | 所有评估局的 `clean_score` 平均值 | `mean(clean_score_i)` | 这是最接近官方最终得分目标的指标，也是最应该保留的第一主指标 | 不能单独使用，因为它会被“少数高分局 + 少数灾难局”的组合掩盖 |
| `SurvivalRate` | 在固定评估配置下，正常完成到 `max_step` 的比例 | `completed_episodes / total_episodes` | 直接衡量模型有没有把整局保下来；对当前赛题尤其重要，因为失败意味着后续潜在收益全部丢失 | 等价于当前 benchmark 里的 `win_rate` / `completed_rate`；在这个赛题里它不是附属指标，而是与得分同级的重要指标 |
| `CPS_all` | 所有评估局总体的“每步清扫得分” | `sum(clean_score_i) / sum(finished_steps_i)` | 反映“每消耗一步，平均能换来多少有效清扫”，比单纯看总分更能体现路径效率 | 不建议用 `mean(clean_score_i / steps_i)`，因为逐局平均容易被极短失败局放大或扭曲；用总分子 / 总分母更稳 |
| `BatteryFailRate` | 电池耗尽失败比例 | `battery_fail_episodes / total_episodes` | 直接对应当前主瓶颈，能把“没学会回充时机”从总失败里单独剥出来 | 应该始终和 `CollisionFailRate` 一起看 |
| `CollisionFailRate` | 碰撞失败比例 | `collision_fail_episodes / total_episodes` | 直接对应短时安全能力，与 `BatteryFailRate` 一起构成失败结构分解 | 适合和 `SurvivalRate` 同时汇报 |
| `P10CleanScore` | 所有评估局 `clean_score` 的 10 分位数 | `percentile(clean_score, 10%)` | 衡量“坏局到底坏到什么程度”，比只看平均分更能发现 catastrophic failure | 如果不方便直接做分位数，也可以用 `LowerTailMean`：最差 20% 局的平均 `clean_score`。当前这个赛题很需要这种低尾指标，因为平均分可以被少数高分局抬起来，但实际训练里真正拖后腿的往往是少数 hard case 崩盘 |

### 13.2 正式主指标的使用建议

我不建议把所有模型优劣压成一个神秘总分。

更合理的做法是：

#### 默认汇报口径

每次正式评估，至少同时汇报 6 项：

| 必报项 | 用途 |
|---|---|
| `AvgCleanScore` | 主结果 |
| `SurvivalRate` | 生存/完成情况 |
| `CPS_all` | 效率解释 |
| `BatteryFailRate` | 长期回充失败结构 |
| `CollisionFailRate` | 短时安全失败结构 |
| `P10CleanScore` | 低尾风险 |

#### 推荐排序规则

如果必须选“哪个 checkpoint 更好”，推荐按下面顺序判：

1. `AvgCleanScore`
2. `SurvivalRate`
3. `BatteryFailRate`
4. `CollisionFailRate`
5. `P10CleanScore`
6. `CPS_all`

原因：

- 官方目标首先还是清扫得分
- 但存活率和失败结构必须同步看
- `CPS_all` 很重要，但更适合作为效率解释量，而不是第一裁判

### 13.3 分解型客观指标

这些指标不是最终裁判，但它们对理解“为什么变好/变差”非常关键。

| 指标 | 定义/公式 | 意义 | 判读方式 |
|---|---|---|---|
| `AvgFinishedSteps` | 平均每局实际结束步数 | 可以区分“分数低是因为早死”还是“虽然活着但效率低” | 应与 `SurvivalRate` 和 `AvgCleanScore` 一起看 |
| `CPS_win` | 只在 `completed` 局上统计清扫效率；`sum(clean_score_i for completed) / sum(finished_steps_i for completed)` | 把“活下来后到底会不会扫”单独拿出来看；与 `CPS_all` 搭配后很有解释力 | `CPS_win` 高、`SurvivalRate` 低，说明会扫，但保不住局；`CPS_win` 低、`SurvivalRate` 高，说明保守但不高效 |
| `AvgChargeCount` | 平均每局充电次数 | 这是有用指标，但绝不是越高越好；它只能说明策略在多大程度上依赖回充循环 | 太低可能是不会回充；太高可能是过早或过频繁回充；它是解释指标，不是主指标 |
| `ChargeEfficiency` | 每次充电平均支撑了多少有效清扫得分；`clean_score / max(charge_count, 1)` | 能帮助判断“会充电”是不是以牺牲整体效率为代价 | 应与 `AvgChargeCount`、`CPS_all` 联合解释 |
| `RemainingChargeOnCompletion` | 只在 `completed` 局统计结束时剩余电量均值 | 反映策略是否过度保守 | 如果剩余电量始终过高，同时 `CPS_win` 偏低，说明模型回充过早或过于保守 |
| `InvalidMoveRate` | 无效移动占比 | 直接反映卡墙、穿角失败、局部震荡；这是路径质量与局部控制的重要客观指标 | 可解释 CPS 下降和生存裕量流失 |
| `PerMapVariance` | 各地图平均得分的标准差或极差 | 衡量跨地图稳定性，比只看总平均更能暴露“某些地图完全不会” | 是地图泛化能力的直接横截面 |
| `ProfileSurvival` | 按 `anchor / mild / broad` 分开统计 survival | 用来回答“是整体都变好了，还是只在简单局更好” | 适合和 curriculum / benchmark profile 一起汇报 |

### 13.4 建议新增的结构性诊断指标

下面这些指标目前未必都已经稳定接入现有 benchmark，但从任务本质出发，我认为它们非常值得补。

| 指标 | 定义 | 意义 | 备注 |
|---|---|---|---|
| `LateReturnRate` | 在 battery fail 局中，第一次进入 return/charge 模式时，`charger_slack < 0` 的比例 | 这是最直接的“回充触发太晚”指标；它比单看 `BatteryFailRate` 更强，因为它能回答：是“不会回”，还是“回得太晚” | 强烈建议补进 benchmark 结果 |
| `ReturnTriggerStepRatio` | 第一次进入 return 模式的步数 / 该局结束步数 | 衡量回充启动相位；对当前赛题尤其关键 | 可分别统计全部局均值和 battery fail 子集均值 |
| `ChargeSuccessRate` | 在出现明确回充意图的局中，最终至少成功充到一次电的比例 | 区分“不会开始回充”和“开始了但执行失败” | 对拆解 battery fail 很有帮助 |
| `RevisitRate` | 访问过的已清洁格占总移动步数的比例 | 量化“绕圈”和重复覆盖问题；对 CPS 和长局效率解释力很强 | 适合和 `InvalidMoveRate` 一起看 |
| `NpcPressureLoss` | 因 NPC 抢先清扫导致的潜在区域收益损失估计 | 如果能做出来，会非常有价值，因为它直接刻画模型是不是在错过时间敏感区域 | 实现更复杂，但值得做 |

### 13.5 训练判读辅助指标

下面这些指标不适合做最终模型优劣判断，但非常适合在训练过程中辅助判读。

#### 一类：训练稳定性指标

| 指标 | 用途 | 注意 |
|---|---|---|
| `entropy` | 判断训练是否塌缩、是否过度确定化 | 不是性能指标，只能回答“训练过程健康不健康” |
| `policy_loss` | 判断策略更新方向和幅度是否异常 | 不能单独说明任务表现 |
| `value_loss` | 判断 critic 是否失控 | 只能说明拟合状态，不能直接说明模型强弱 |
| `total_loss` | 观察整体训练过程是否稳定 | 更适合趋势观察，不适合横向比较模型 |

#### 二类：学习方向指标

| 指标 | 用途 |
|---|---|
| `avg_expert_weight` | 判断模型是否越来越依赖 Expert |
| `avg_charge_count` | 判断策略是否在回充循环上发生明显漂移 |
| `avg_clean_per_step` | 判断效率是在上升还是在用保守换存活 |
| `avg_invalid_move_rate` | 判断局部控制质量是否在恶化 |
| `battery_fail_rate` | 判断长期失败结构是否在转移 |
| `collision_fail_rate` | 判断短时安全失败结构是否在转移 |

#### 三类：泛化和分布指标

| 指标 | 用途 |
|---|---|
| `anchor_win_rate` | 判断简单配置是否稳定 |
| `mild_win_rate` | 判断中等扰动配置是否在进步 |
| `broad_win_rate` | 判断 hard profile 是否真在变强 |
| `per_map_variance` | 判断跨地图稳定性是否改善 |
| `config_risk hotspot` | 判断是否有固定配置组合持续崩盘 |

### 13.6 不建议拿来当主指标的量

下面这些量有用，但不应该被当成模型优劣的正式主指标。

| 指标 | 为什么不适合当主指标 |
|---|---|
| `Shaped reward / total_reward` | 它依赖当前 reward 设计；版本之间 reward 一旦变化，就不可横向比较 |
| `AvgChargeCount` | 充电次数不是越多越好，也不是越少越好；它只能做解释变量 |
| `Entropy` | entropy 高不等于策略好，entropy 低也不等于策略坏；它只是探索程度和训练状态的信号 |
| `PolicyLoss / ValueLoss` | 它们反映的是优化过程，不是任务完成质量 |

### 13.7 推荐的一套最终指标面板

如果后续要统一训练/benchmark/报告口径，我建议固定一套面板。

#### 正式评估面板

| 面板项 | 角色 |
|---|---|
| `AvgCleanScore` | 主结果 |
| `SurvivalRate` | 主结果 |
| `CPS_all` | 效率解释 |
| `BatteryFailRate` | 失败结构 |
| `CollisionFailRate` | 失败结构 |
| `P10CleanScore` | 低尾风险 |
| `ProfileSurvival(anchor/mild/broad)` | 分布切片 |
| `PerMapVariance` | 泛化稳定性 |

#### 训练监控面板

| 面板项 | 角色 |
|---|---|
| `AvgCleanScore` | 结果趋势 |
| `SurvivalRate` | 结果趋势 |
| `CPS_all` 或 `avg_clean_per_step` | 效率趋势 |
| `BatteryFailRate` | 长期失败结构 |
| `CollisionFailRate` | 短时失败结构 |
| `AvgChargeCount` | 回充行为漂移 |
| `ChargeEfficiency` | 回充收益质量 |
| `InvalidMoveRate` | 局部控制质量 |
| `Entropy` | 训练稳定性 |
| `PolicyLoss` | 训练稳定性 |
| `ValueLoss` | 训练稳定性 |
| `AvgExpertWeight` | Expert 依赖程度 |

#### 深度诊断面板

| 面板项 | 角色 |
|---|---|
| `LateReturnRate` | 回充是否太晚 |
| `ReturnTriggerStepRatio` | 回充启动相位 |
| `ChargeSuccessRate` | 回充执行是否真正成功 |
| `RevisitRate` | 路径重复问题 |
| `RemainingChargeOnCompletion` | 是否过度保守 |

### 13.8 一句话建议

对于这道题，我认为最合理的正式判断口径不是“只看 clean score”，也不是“只看存活率”，而是：

> 用 `AvgCleanScore + SurvivalRate` 判断主效果，  
> 用 `BatteryFailRate + CollisionFailRate + P10CleanScore` 判断失败结构和低尾风险，  
> 用 `CPS_all + ChargeEfficiency + InvalidMoveRate + LateReturnRate` 判断策略为什么会这样。

这样做的好处是：

- 不会把效率误判成存活
- 不会把保守误判成进步
- 不会把少量高分局误判成整体提升
- 能直接对齐当前赛题的真实主矛盾
