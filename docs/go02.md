# go02

目标：基于当前 `go01` 双步数训练日志，诊断“整体分数偏低”的主要原因，并提出下一步提高方案。

本文件原始版本是诊断与方案设计；当前已完成第一轮代码落地。

## 1. 诊断依据

本轮主要依据：

- `train/log/aisrv/aisrv_kaiwu_rl_helper_pid314_log_2026-04-23-01.log`
- `train/log/learner/learner_train_pid226_log_2026-04-23-01.log`

其中最关键的训练现象已经很明确：

- `1000 / 1000 / 2000` 双步数训练已经实际生效
- `2000` 步局确实进入 rollout，并非只在配置层切换
- 但整体分数仍然偏低，且存在一些明显塌局

## 2. 关键现象整理

### 2.1 `1000` 步局整体表现

`1000` 步局多数表现集中在：

- `score ≈ 885 ~ 956`
- 多数能跑满 `1000`

典型成功局：

- `ep=1`：`911`
- `ep=2`：`903`
- `ep=5`：`947`
- `ep=10`：`915`
- `ep=11`：`939`
- `ep=20`：`954`

说明：

- 当前 baseline 在 `1000` 步配置下并没有完全失控
- 但也没有形成明显高分态

### 2.2 `2000` 步局表现两极分化

`2000` 步局的表现呈现“高分成功 + 极端早停失败”并存：

- `ep=96`：`steps=2000`, `score=1773`

#### 失败局

- 真正的问题是：`2000` 步局稳定性不够，存在明显长尾塌局

### 2.3 失败局高度集中在 `mode=charge`

从日志看，绝大多数失败局都呈现：

- `mode=charge`
- `alpha=0.010`

这说明失败局不是因为“自由探索太多”，而是：

- 进入回桩阶段后仍然失败
- 也就是“回桩时机/回桩路径/充电节奏”仍然是主矛盾

这点在 `2000` 步局里尤其明显。

## 3. 问题本质判断

## 3.1 当前不是“不会利用 2000 步”

如果模型真的不会利用 `2000` 步，它会表现为：

- 大多数 `2000` 步局也只打出略高于 `1000` 步局的分数
- 或者很少跑满 `2000`

但现在不是这样。

当前 `2000` 步成功局能稳定打到：

- `1696 ~ 1888`

说明模型已经学会：

- 在更长预算下继续探索
- 而不是简单照搬 `1000` 步节奏

## 3.2 真正问题是“长局稳定性不足”

`2000` 步局比 `1000` 步局更难的地方在于：

- 需要更多次回桩
- 需要更稳定的中后期充电节奏
- 更容易在后程出现一次回桩失败导致整局塌掉

所以当前最主要的矛盾不是：

- “探索不够”

而是：

- “长局里回桩闭环还不稳定”

## 3.3 当前 reward/planner 更像在优化 `1000` 步局稳定性

当前 baseline 的很多设计，本质上是在固定 `1000` 步环境里长出来的：

- reward 的时间尺度
- planner 的保守阈值
- 扩张阶段长度
- 回桩触发节奏

当切到 `2000` 步局时：

- 有些成功局说明“方向没错”
- 有些失败局说明“规则还没有完全适配长局”

也就是说：

- `go01` 已经证明“扩步数训练是可行的”
- 但还没有解决“长局回桩稳定性”的问题

## 4. 训练日志给出的提高方向

## 4.1 第一优先级：针对 `2000` 步局单独做回桩稳定性增强

因为问题已经不是探索能力，而是长局收尾和中后期生存。

建议下一步改动重点：

- 只在 `max_step=2000` 场景下，轻量增强回桩保守度
- 不要全局增强，否则容易伤到 `1000` 步局

优先考虑的方向：

- `BASE_RETURN_MARGIN` 条件化
- `LOW_BATTERY_RATIO` 条件化
- `EXIT_RETURN_RATIO` 条件化

核心思路：

- `2000` 步局允许更长探索，但不能拖到过晚才回桩
- 中后段要更早建立安全循环

## 4.2 第二优先级：让 planner 感知“当前是长局”

虽然当前已经把 `max_step_norm + step_ratio` 注入到了模型输入，
但 planner 本身还没有显式按 `max_step` 调整行为。

最值得优先改的不是全部逻辑，而是：

### 扩张阶段长度

当前：

- `AGGRESSIVE_EDGE_STEPS = 500`

对 `2000` 步局可能偏短。

建议后续改成条件版本：

- `1000` 步局：维持当前
- `2000` 步局：适度延长

### 回桩缓冲

当前失败局大量卡在 `charge` 模式，因此：

- `2000` 步局应比 `1000` 步局略早进入安全回桩

## 4.3 第三优先级：监控里分开看 `1000` 与 `2000`

当前已经能在日志中看见：

- `max_step=1000`
- `max_step=2000`

后面必须进一步拆开看两个子分布：

- `1000` 步局 success rate / avg score
- `2000` 步局 success rate / avg score

否则整体均值会掩盖真实问题。

举例：

- 如果整体均值下降，但 `2000` 成功局其实变强了
- 那说明问题是长尾失败，而不是全局退化

## 4.4 第四优先级：不要马上大改 reward 主体

当前 reward 已经相对复杂，而且 `2000` 步成功局并不差。

这说明：

- reward 主方向不是完全错的

所以现在不建议马上大改：

- `cleaning_reward`
- `explore_reward`
- `charge_event_reward`

否则容易把已经能打出来的 `2000` 成功局一起打掉。

更合理的是：

- 先从 planner 的条件化阈值下手
- 再看是否还有必要做 reward 微调

## 5. go02 具体方案

go02 建议定义为：

- **长局稳定性增强方案**

核心目标：

- 保住 `1000` 步局现有水平
- 提高 `2000` 步局成功率
- 压低 `2000` 步局的极端早停概率

### go02 建议优先改动项

1. `planner` 中引入 `max_step` 条件化阈值
2. 重点服务 `2000` 步局的回桩节奏
3. 保持 `1000` 步局策略尽量不受伤

### go02 不建议优先改动项

1. 不建议先改网络结构
2. 不建议先大改 reward
3. 不建议先大调 PPO 主参数

## 6. go02 成功标准

go02 的成功标准不应该只看均值，而应该重点看：

### `1000` 步局

- 成功率不明显下降
- 分数保持在当前区间

### `2000` 步局

- 成功局继续保持 `1700+`
- 失败局比例下降
- 极端塌局（`steps < 800`）减少

## 7. 结论

当前整体分数偏低，不是因为：

- 双步数训练方向错了

相反，日志已经证明：

- `2000` 步局是能打出来高分的

真正的问题是：

- 长局稳定性不够
- 回桩阶段是当前主要薄弱点

所以 go02 不应该定义成“提高整体探索强度”，而应该定义成：

- **围绕 `2000` 步局回桩稳定性做条件化增强**

这是目前最符合日志证据的提高方向。

## 8. 本轮实际落地

本轮按 go02 的主线，只做了长局稳定性增强：

- 只改 planner 的 `2000` 步局条件化阈值
- 不改 reward 主体
- 不改 PPO 主参数
- 不改网络结构

### 8.1 修改文件

- `code/agent_ppo/algorithm/algorithm.py`
- `agent_ppo/algorithm/algorithm.py`
- `code/agent_ppo/agent.py`
- `agent_ppo/agent.py`
- `code/agent_ppo/workflow/train_workflow.py`
- `agent_ppo/workflow/train_workflow.py`

### 8.2 实际参数变化

本轮没有直接改基础常量，而是新增了针对 `max_step >= 2000` 生效的条件化阈值：

```python
effective_return_margin = BASE_RETURN_MARGIN + 6.0
effective_low_battery_ratio = LOW_BATTERY_RATIO + 0.04
effective_exit_return_ratio = EXIT_RETURN_RATIO + 0.02
effective_aggressive_edge_steps = 800
```

映射到当前 baseline 常量，实际效果为：

```python
BASE_RETURN_MARGIN: 22.0 -> 28.0   (仅 2000 步局)
LOW_BATTERY_RATIO: 0.30 -> 0.34    (仅 2000 步局)
EXIT_RETURN_RATIO: 0.95 -> 0.97    (仅 2000 步局)
AGGRESSIVE_EDGE_STEPS: 500 -> 800  (仅 2000 步局)
```

对 `1000` 步局：

- 所有阈值维持 baseline 不变

### 8.3 条件化接入位置

这些条件化阈值已经接入：

- `should_charge`
- `on_charger` 后退出返回模式
- coverage target 选择中的 `reserve`
- 扩张阶段判定

### 8.4 设计目的

这轮修改的目标是：

- 保住 `1000` 步局当前表现
- 让 `2000` 步局更早建立安全回桩闭环
- 降低长局后程塌局
- 同时给 `2000` 步局更长的扩张阶段，避免仍按 `1000` 步节奏过早收缩

### 8.5 当前边界

这一轮仍然没有做：

- reward 的步数尺度修正
- 更细粒度的 `charge_count / remaining_charge` 条件化奖励
- `max_step` 相关的 residual alpha 调整

所以当前 go02 仍然是：

- 以 planner 条件化为主
- 先修长局稳定性
- 暂不大改学习目标
