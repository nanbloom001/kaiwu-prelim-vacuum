# go23-0

目标：综合 [docs/go23-1.md](/E:/competition/kaiwuFinal/26fwwb/docs/go23-1.md) 与 [docs/go24-1.md](/E:/competition/kaiwuFinal/26fwwb/docs/go24-1.md) 的有效思路，对原 go23 进行覆盖式收敛，形成一版 **不改模型保存链路、不改导出链路、不碰训练兼容性敏感部分** 的优化方案，专门规避：

- 前期训练长时间起不来
- 首局过长导致 learner 长时间无样本
- go23 之后训练启动变慢
- 近 NPC / charge 场景下局部打转

go23-0 的定位不是继续堆复杂机制，而是做一版 **低风险、低开销、优先保证训练能顺利起量** 的过渡方案。

---

## 1. 核心原则

go23-0 必须遵守以下边界：

- 不改 `save_model()` 触发方式
- 不改 `backup_model / user_ckpt_dir / model_file_save` 链路
- 不改 `modelpool` 保留策略
- 不改训练容器、导出容器、签名链路

允许优化的范围只包括：

- reward credit 的确认方式
- planner 的中间态能力
- 前期样本启动速度
- 每帧计算开销

一句话总结：

- **go23-0 只解决“训练为什么起不来 / 为什么起得慢 / 为什么前期卡死”，不处理模型保存与导出兼容问题。**

---

## 2. 三份方案中值得保留的思路

### 2.1 来自原 go23 的有效部分

原 go23 的方向判断是正确的：

- `arrival` 奖励确认过宽
- 很多“到桩后不久 charge FAIL”的轨迹被误当成正样本
- 问题不在于奖励太少，而在于 credit 给得太早、太轻

因此 go23-0 保留下面两个核心思想：

1. `arrival reward` 不再即时发放
2. `arrival reward` 要延迟确认，并绑定最基本的生存条件

但 go23-0 不采纳原 go23 那种更重的全套状态机做法：

- 不引入 `candidate_confirmed / final_confirmed / retro_cancel` 全套复杂机制
- 不引入过多 episode 末追责字段
- 不让 reward gating 本身成为新的性能瓶颈

---

### 2.2 来自 go23-1 的有效部分

go23-1 对 planner 的判断也是对的：

- 当前失败不只是 reward 问题
- 很多问题来自 planner 缺少“危险时先脱困”的中间态

go23-0 保留其核心思想，但采用弱化版本：

1. 近 NPC 时，目标推进优先级下调
2. 危险窗口内，允许短时以脱困为先

go23-0 不直接采纳 go23-1 的重版本：

- 不做完整 `charge retarget`
- 不做复杂多桩重排序
- 不做 charger 冷却系统
- 不做完整 escape 评分重构

原因很简单：

- 这些改动方向是对的
- 但会显著提高 planner 复杂度和调试成本
- 对“前期训练起不来”这个当前主问题并不是最短路径

---

### 2.3 来自 go24-1 的有效部分

go24-1 最大的价值不是行为策略，而是性能诊断：

- charger region 解析
- pending arrival 状态管理
- 新增特征维度与派生统计

这些东西一旦每帧做重计算，就会直接把首局时间拉长。

因此 go23-0 采纳 go24-1 的工程原则：

- 先缓存
- 先降频
- 先避免重复解析
- 不在每帧关键路径上塞过重逻辑

但 go23-0 不做太激进的工程重构：

- 不做多层后台清理机制
- 不做复杂 grid 索引系统
- 不做大规模函数拆分

原因是：

- 当前优先级是“训练先稳稳起量”
- 不是做一版高复杂度性能框架

---

## 3. go23-0 的正式方案

go23-0 只做四件事。

### 3.1 `arrival reward` 改为轻量延迟确认

不再采用“到桩立即给分”。

但也不采用原 go23 的重型多阶段确认。

go23-0 的折中做法：

1. 到达新 charger 后先进入 `pending`
2. 经过一个最小延迟窗口后再确认
3. 只有在窗口内出现了最基本的有效收益，才给 reward
4. 如果在窗口内很快进入明显 charge 困局，则直接取消

这里的“最基本有效收益”只要求轻量条件，例如：

- 一定量 `coverage_gain`
- 或一定量 `observed_gain`
- 或离开当前桩区域后仍有正向推进

这里的“明显困局”只要求低成本判定，例如：

- 充电态下长时间无新观测、无清扫、无电量改善
- 低电量且仍未摆脱危险区

这样做的目的：

- 避免“摸到桩就赚”
- 但又不把 credit gating 做成新的性能热点

---

### 3.2 近 NPC 时只做弱 escape，不做完整 planner 重构

go23-0 认为：

- 当前 planner 的问题不是完全不会躲
- 而是在危险窗口里，目标推进奖励仍然太强

因此只做一个低成本的策略修正：

当 `nearest_npc_distance` 很小，且动作空间明显收缩时：

- 下调 path 对齐奖励
- 下调朝目标推进奖励
- 提高远离 NPC 的局部动作优先级

这里不需要引入：

- 完整的 `escape mode` 状态机
- 大量额外日志
- 多桩切换逻辑

目标不是让 planner 更“聪明”，而是让它在高危几帧里不要继续执着追目标。

---

### 3.3 前期训练启动优先保证“尽快出样本”

当前训练起不来的根本原因不是 learner 慢，而是：

- episode 太长
- 样本输出太晚
- learner 长时间 `input ready size = 0`

因此 go23-0 的核心取舍是：

- 前期不追求把每局都跑得很完整
- 优先避免极长局拖到 10~20 分钟才出首批样本

所以 go23-0 允许加入 **低成本慢局保护**，但只保留最低复杂度版本：

- 不刷大量 warning 日志
- 不做多层 wall-time 诊断
- 不做复杂的 episode 在线分析
- 只在低频节点上检查“是否明显低效”

如果满足典型低效条件，则直接终止当前局，让训练尽快进入下一局、尽快产样本。

---

### 3.4 性能优化优先做缓存和降频

go23-0 只采纳最稳妥的性能优化：

1. charger region 缓存
2. organs 不变时不重复解析
3. pending arrival 只做最小必要检查
4. 慢变化特征降频更新
5. 避免每帧重复做大对象遍历和重复距离计算

不采纳的内容：

- 复杂索引系统
- 大规模函数拆分
- 高维护成本的后台流程

理由：

- 当前痛点是首局慢、首样本迟
- 用缓存和降频就能解决大头
- 没必要把代码复杂度一口气抬太高

---

## 4. go23-0 的明确取舍

### 4.1 明确采纳

- 原 go23 的“延迟确认 arrival reward”思想
- go23-1 的“危险时先弱化目标牵引”思想
- go24-1 的“缓存 / 降频 / 避免每帧重复计算”思想

### 4.2 明确不采纳

- `candidate_confirmed / final_confirmed / retro_cancel` 全套复杂 credit 状态机
- 完整 charger 多桩重排序体系
- 危险桩 cooldown 体系
- 大量慢局 warning 日志
- 与训练保存、导出、签名链路有关的任何改动

---

## 5. go23-0 的实施边界

go23-0 允许修改的代码范围应当限制在：

- `agent_ppo/feature/preprocessor.py`
- `agent_ppo/algorithm/algorithm.py`
- 必要时少量 `agent_ppo/workflow/train_workflow.py` 的低频慢局保护

go23-0 明确禁止触碰：

- `save_model` 逻辑
- `backup_model / user_ckpt_dir`
- `model_file_save`
- `modelpool` 配置
- docker / env 导出链路

---

## 6. 预期效果

go23-0 预期首先改善的不是最终分数，而是训练可启动性：

1. learner 更快收到第一批样本
2. 首局 / 前几局不再超长卡死
3. 近 NPC / charge 场景下局部打转减少
4. `arrival reward` 不再过早把坏轨迹认成正样本
5. 每帧特征与规则计算成本下降，训练起量速度恢复

允许短期波动的指标：

- 某些局会更早结束
- 早期平均分可能轻微波动
- 首次到桩时间可能略慢

这是可以接受的，因为 go23-0 的优先级是：

- **先让训练稳定起得来，再让策略变得更强。**

---

## 7. 一句话总结

go23-0 的本质是：

- **轻量收紧 arrival credit，弱化危险窗口内的目标执念，并通过缓存与降频降低每帧开销，从而避免前期训练长时间起不来；同时明确不触碰模型保存和导出链路，以保证后续训练兼容性。**
