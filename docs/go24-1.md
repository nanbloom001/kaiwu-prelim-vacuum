### 1.2 关键发现

🔴 **问题不是"启动变慢"，而是"运行时累积下降"**

后期训练（Ep3, Ep8, Ep10, Ep11）出现严重性能下降（6-8步/秒），说明：

1. **前期正常** (Ep0-Ep2): 10-16 步/秒
2. **第一次下降** (Ep3): 135秒 (7.4步/秒) - 性能下降30%
3. **短暂恢复** (Ep4-Ep7): 回到10 步/秒
4. **严重下降** (Ep8+): 140+秒 (6-8步/秒) - 性能下降35-40%

**推测原因**：

1. ✅ **内存未释放** - `pending_arrivals` / `confirmed_charger_arrival_steps` 等字典累积
2. ✅ **set查询变慢** - `visited` 集合和 `rewarded_arrived_charger_regions` 越来越大
3. ✅ **没有清理机制** - `charger_arrival_steps` / `retro_canceled_arrivals` 永不清理
4. ✅ **Python GC压力** - 大量字典/集合操作导致垃圾回收周期增长

### 1.3 为什么是累积问题而非帧时间问题

**证据**：
- Ep1/Ep2 (355-666步) 反而比 Ep0 (1000步) 更快
- Ep9 (单局) 达到14.3步/秒，这说明单帧处理能力正常
- 但 Ep3-Ep8 (局数累计) 明显下降，说明**跨局的状态累积**

**结论**：问题根源是 `Preprocessor` 的 `reset()` 函数**没有完全清理**go23新增的数据结构

## 2.2 策略二：优化pending_arrivals清理时机

**问题**：

当前 `finalize_episode_rewards()` 只在 episode 结束时清理，但：
1. 某些 pending_arrivals 可能在episode中途就应该清理

```python
def finalize_episode_rewards(self, *, result_str: str, final_mode: str, final_step: int) -> float:
    """Episode结束时的奖励最终确定与完整清理"""
    reward = 0.0
    is_charge_fail = result_str == "FAIL" and final_mode == "charge"
    final_step = int(final_step)

    for region_key, info in list(self.pending_arrivals.items()):
        # ... 原有逻辑 ...
    
    # 新增：episode结束时，完整清理pending_arrivals
    # (原代码只是del某些项，但empty的entry不清)
```

## 2.3 策略三：优化set查询性能

**问题**：

`visited` 集合和 `rewarded_arrived_charger_regions` 在后期局数可能包含数千个元素，每次 `pos in set` 查询都会扫描哈希表。

```python
# 每帧执行，累计1000步，每步可能调用多次
is_on_charger = any(self.cur_pos in region for region in self.charger_regions)
```

当 `charger_regions` 长度大时，这会成为瓶颈。

**优化方案**：

```python
def __init__(self):
    self.reset()
    self._charger_pos_set = set()  # 新增：快速查询

def pb2struct(self, env_obs: dict, last_action: int):
    # 原有的charger_regions解析...
    self.charger_regions = self._parse_charger_regions(env_obs.get("organs", []))
    
    # 新增：构建快速查询集合
    self._charger_pos_set.clear()
    for region in self.charger_regions:
        for pos in region:
            self._charger_pos_set.add(pos)

def _is_on_charger_fast(self) -> bool:
    """快速检查是否在充电桩上"""
    return self.cur_pos in self._charger_pos_set
```

**预期效果**：
- `O(any(... in region))` 变为 `O(pos in set)`
- 单次查询从 O(n×m) 降至 O(1)
- **每帧减少0.1-0.2ms** ✅

## 2.4 策略四：增量化pending_arrivals遍历

**问题**：

`_resolve_pending_arrivals()` 每帧都遍历所有 pending_arrivals，但大多数arrival在确认后不会再改变状态。

```python
for region_key, info in list(self.pending_arrivals.items()):
    # ... 复杂的状态检查 (20+ 行代码) ...
```

当pending_arrivals从 4-6 个增长到 20+ 个时，这变成显著瓶颈。

**优化方案**：

```python
def _resolve_pending_arrivals(self, ...) -> float:
    reward = 0.0
    
    # 仅处理"活跃"的到达记录
    # 已确认且距离当前步骤足够远的，直接跳过
    
    for region_key, info in list(self.pending_arrivals.items()):
        # 快速过滤1：已final_confirmed且距confirm已超过200步，跳过
        if (info.get("final_confirmed") and 
            self.step_no - info.get("confirm_step", 0) > 200):
            continue
        
        # 快速过滤2：arrival太久以前（>500步）还未confirmed，清理
        if (not info.get("final_confirmed") and 
            self.step_no - info.get("arrival_step", 0) > 500):
            self.arrival_canceled_count += 1
            del self.pending_arrivals[region_key]
            continue
        
        # ... 仅处理活跃状态的到达 ...
    
    return reward
```

**预期效果**：
- pending_arrivals中的99%的项被快速跳过
- 仅1-2个活跃到达被详细检查
- **每帧减少0.3-0.5ms** ✅

## 2.5 策略五：周期性数据结构整理

**问题**：

Python的dict和set在大量删除后，内部hash表不会自动收缩，导致空间浪费和查询变慢。

**优化方案**：

```python
def pb2struct(self, env_obs: dict, last_action: int):
    # ... 原有逻辑 ...
    
    # 每1000步进行一次整理（局结束时自动触发）
    if self.step_no > 0 and self.step_no % 1000 == 0:
        self._cleanup_dicts()

def _cleanup_dicts(self):
    """定期整理数据结构，强制Python重新hash"""
    # 通过临时变量重建dict，强制hash表收缩
    if self.pending_arrivals:
        temp = dict(self.pending_arrivals)
        self.pending_arrivals.clear()
        self.pending_arrivals.update(temp)
    
    if self.confirmed_charger_arrival_steps:
        temp = dict(self.confirmed_charger_arrival_steps)
        self.confirmed_charger_arrival_steps.clear()
        self.confirmed_charger_arrival_steps.update(temp)
```

**预期效果**：
- 强制Python GC并重建hash表
- 恢复查询和迭代性能
- **每1000步开销<10ms（仅局结束）** ✅
