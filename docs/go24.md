# go24：后续优化整合方案

## 1. 目标定义

go24 不再拆成彼此孤立的多版思路，而是整合为一条连续优化路线，按下面顺序推进：

1. 先解决 **性能随局数累积下降** 的问题，恢复稳定训练速度。
2. 再解决 **提前结束、充电失败、完成度不足** 的问题，保证大多数局能稳定跑满 `1000` 步。
3. 在生存与完成度基本稳定后，把重点切到 **平均有效得分率提升**，压缩无效步数，提高中后期收分效率。

一句话概括：

- **go24 是“先稳性能，再稳生存，最后提均分”的统一优化方案。**

---

## 2. 四份文档的整合结论

### 2.1 `go24-1` 的有效结论

`go24-1` 提供了最明确的问题指向：

- 当前主要性能问题不是单帧算力不足，而是 **跨局状态累积未清理**
- 根因高度集中在 `preprocessor.reset()` 没有完整清掉 go23 新增状态
- 优先级最高的是 **完整 reset + episode 结束显式清理**

这个方向应作为 go24 的 **Phase A**，且优先于任何策略调参。

### 2.2 `go24-2` 与 `go24-4` 的整合结论

`go24-2` 和 `go24-4` 基本是同一类方案，核心共识是：

- 当前低分局的重要来源是 **charge 阶段失败导致提前结束**
- arrival reward 偏弱、charge loop 判定偏严，可能让策略“不敢充”或“充得不稳定”
- 后续需要围绕 **完成度、充电时机、充电安全性** 做策略修正

这部分应作为 go24 的 **Phase B**。

但有一条需要修正：

- 原文里的 `completion_bonus` 实际写法是“提前结束反而加正奖励”，这会削弱 fail 惩罚，不适合作为默认主方案。
- 整合后应改成 **completion penalty / early termination penalty**，即：越早结束，终局惩罚越重，而不是越轻。

### 2.3 `go24-3` 的有效结论

`go24-3` 的判断成立，但前提是：

- 只有当大多数局已经能稳定打满 `1000` 步，优化重点才应该从“活下来”切到“提分”

因此 `go24-3` 不应和前两阶段并行混做，而应作为 **Phase C**：

- 聚焦中后期 score harvesting
- 压缩无效步数
- 建模充电机会成本

## 3. go24 总体路线图

## Phase A：性能稳定化

### 3.1 目标

解决训练过程中 6.9~16.1 步/秒的大幅波动，重点消除跨局累积导致的后期变慢。

### 3.2 核心判断

最可能根因是 go23 引入的状态结构没有在 episode reset 时完整清理，包括但不限于：

- `charger_regions`
- `rewarded_arrived_charger_regions`
- `charger_arrival_steps`
- `confirmed_charger_arrival_steps`
- `pending_arrivals`
- `candidate_charger_arrival_steps`
- `retro_canceled_arrivals`

### 3.3 必做项

1. 在 `code/agent_ppo/feature/preprocessor.py` 的 `reset()` 中完整清理 go23 新增局内状态。
2. 在 episode 结束逻辑里对 `pending_arrivals` 做显式 `.clear()`，避免残留引用。
3. 重置所有与 arrival/charge 统计有关的计数器，避免跨局污染。

### 3.4 可选项

1. 为 charger 区域增加快速查询缓存，如 `_charger_pos_set`。
2. 对 `_resolve_pending_arrivals()` 增加活跃项过滤，减少每帧无效遍历。
3. 必要时增加低频的数据结构重建，但这项优先级最低，只有在前两项完成后仍有性能问题才考虑。

### 3.5 验证指标

- 平均训练速度
- 最慢局速度
- 速度标准差
- 连续多局训练后是否仍出现明显降速趋势

### 3.6 成功标准

- 平均速度恢复到稳定区间
- 最慢局不再明显掉到 `7` 步/秒附近
- 性能波动显著收敛

## Phase B：完成度与充电策略稳定化

### 4.1 目标

在性能稳定后，优先解决：

- 提前结束
- charge 相关失败
- 低完成度导致的低分局

目标不是先追求高分，而是先把大多数局稳定推到 `1000` 步。

### 4.2 问题判断

综合 `go24-2/4`，当前问题大概率集中在三类：

1. `arrival reward` 太弱，策略对“安全抵达充电桩”的学习信号不足。
2. `charge loop` 判定过于激进，正常充电行为可能被误判为循环。
3. 到达充电桩后的后续收益判定过严，导致 arrival credit 容易回收或失真。

### 4.3 推荐主改动

#### 4.3.1 调整 arrival 基础奖励

可以提高 `_arrival_base_reward()` 的基础值，但要保持克制，建议：

- 第 1 个新桩：中等增强
- 第 2 个新桩：保留明显衰减
- 第 3 个及以后：只保留弱激励

原则是：

- 让策略愿意去找可用充电资源
- 但不能把“找桩”学成压倒清扫收益的主目标

#### 4.3.2 重写 charge loop 判定

不要再用过小阈值把正常进出 charger 区域判成失败。更合理的 loop 判定应同时考虑：

- 在 charge 阶段持续无新观测
- 持续无清扫收益
- 持续无法脱离局部困境
- 重复回访次数过多

也就是说，只有“长时间无进展”的充电过程才应视为 loop failure。

#### 4.3.3 放宽 arrival 后续确认的极端约束

需要检查 `_resolve_pending_arrivals()` 中这些条件是否过严：

- `coverage_gain`
- `observed_gain`
- `left_region`
- 过长确认窗口里的多次取消逻辑

建议方向：

- 保留 gating，但减少“正常可用 arrival 也被取消”的概率
- 让 step-level credit 更稳定，不要频繁回滚

#### 4.3.4 引入完成度惩罚，而不是完成度奖励

整合后明确采用：

- **越早结束，终局惩罚越强**
- **打满 `1000` 步不额外奖励，只视为基准**

建议终局设计思路：

- 完整局：保持现有 win/fail 终局框架
- 提前结束局：按 `finished_steps / 1000` 追加惩罚项

这样能避免“早死但少亏”的错误激励。

### 4.4 可选改动

1. 增加 `battery trend` 特征，帮助策略判断电量变化方向。
2. 为 planner 增加“当前桩过于危险，应该切换桩”的辅助信号。
3. 只在终局补少量 arrival quality bonus，奖励“找到多个桩且活到后期”的轨迹。

### 4.5 验证指标

- `finished_steps = 1000` 的局占比
- 提前结束局的平均得分
- charge 阶段失败次数
- 平均首次充电步数
- 平均充电次数

### 4.6 成功标准

- 大多数局能稳定跑满 `1000` 步
- 提前结束局显著减少
- 完成度提升的同时，平均分不回退
- 不引入新的明显性能损失

## Phase C：平均有效得分率提升

### 5.1 启动前提

只有当 Phase B 达成后，才建议进入这一阶段。判断标准是：

- 完成度已经稳定
- 早死已不再是主矛盾
- 主要差异变成“同样 `1000` 步，为什么有人 `900+`，有人 `700~800`”

但根据当前最新训练日志，需要补一条更严格的前提：

- **Phase C 的任何改动都不能明显破坏 Phase B 已经建立的完成度与充电稳定性**

也就是说：

- 不能因为“提均分”而重新放大 `mode=charge` 失败局
- 不能因为“压缩无效步”而让本来能跑满的局重新提前结束
- 不能因为“减少低性价比充电”而把必要充电也一起削弱

### 5.2 目标

把更多步数从：

- 探索过度
- 回摆
- 低效绕行
- 低性价比充电

转成：

- 连续清扫
- 中后期高价值得分
- 更高的 `score / finished_steps`

这里需要补充一个新的约束：

- **Phase C 的优化目标必须从“纯提分”改成“保完成度前提下提分”**

因此 go24 后续不再允许直接把 Phase C 作为单向增强项推进，而必须改成：

- 先验证是否拖累 Phase B
- 若拖累，则先收缩或重构 Phase C
- 只有在完成度指标不恶化时，才继续放大提分项

### 5.2.1 当前问题复盘

从最新训练现象看，Phase C 相关策略已经开始出现副作用：

- 虽然存在 `900+` 的满步高分局，但同时重新出现了明显的早死局
- `mode=charge` 的失败局仍然存在，说明“提分”并没有完全建立在“稳充电”之上
- 训练均值里 `finished_steps` 被这类失败局拉低，说明 Phase B 还不能视为完全锁定

这说明当前问题不是“继续按 go24 原方案把 Phase C 往前推”，而是：

- **Phase C 已经开始拖累 Phase B，因此后续策略必须进一步优化，而不是直接照原 go24 继续加码**

### 5.3 三条主线

在保留原三条主线之前，先增加一条新的总原则：

- **Phase C 只能做受控增强，不能改成与 Phase B 对抗的激进提分**

#### 5.3.1 中后期从 frontier 转向 score harvesting

思路是分阶段切换策略重心：

- 前期：扩图、找桩、建立路线
- 中期：扩图与清扫平衡
- 后期：优先兑现已知高价值脏区

建议改法：

1. 中后期提高 `dirt` 目标相对权重。
2. 剩余步数下降后，下调低收益 `frontier` 吸引力。
3. 当已知脏区密度足够高时，优先连续收分而不是继续远探。

但这里需要新增限制：

1. 不允许在前中期过早削弱 `frontier`
2. 不允许在 `charger slack` 不充足时强推 `dirt`
3. 只有在“已知充电桩 + 电量安全余量足够 + 已知脏区密度足够高”同时满足时，才允许明显切向 `dirt`

#### 5.3.2 压缩无效步数

重点打击：

- `无清扫 + 无新观测`
- 小回环
- 高频 revisit
- 长时间停留在低收益区域

建议改法：

1. 强化连续无收益步惩罚。
2. 对短周期小回环做更平滑、连续的惩罚。
3. 对高 revisit 区域增加中后期机会成本。

但这里也要补限制：

1. `无清扫 + 无新观测` 不能直接等价于“无价值”
2. 如果当前动作仍服务于找桩、脱困、回充、跨区过渡，则惩罚必须减弱
3. 充电前后窗口内不能把正常回充路径误打成低效绕行

#### 5.3.3 充电机会成本建模

后续要从“会不会充”升级为“这次充电值不值”。

建议加入：

1. 高电量时的过早充电惩罚。
2. 充电后若没有带来后续收益，则降低这次充电的奖励价值。
3. 末段剩余步数较少时，降低非必要充电倾向。

这里的关键修正是：

1. 机会成本惩罚必须只打击“明显不必要的充电”
2. 不能把“安全必要充电”和“高电量低性价比充电”混在一起
3. 一旦 `battery / charger_distance` 进入风险区，就必须让位给 Phase B 的生存约束

### 5.4 验证指标

- 平均 `score`
- 平均 `score / finished_steps`
- `900+` 局占比
- `500` 步后每 `100` 步得分
- `700~1000` 步区间清扫增量
- 无收益步数占比

除了上述提分指标，go24 现在必须增加一组 **Phase B 保护指标**：

- `finished_steps = 1000` 的局占比是否回退
- `mode=charge` 失败局占比是否上升
- 提前结束局平均结束步数是否下降
- `arrival_confirmed_count` 是否回退
- `charge_fail_after_arrival` 是否上升

### 5.5 成功标准

- 在完成度不下降前提下，平均有效得分率持续上升
- `900+` 高分局比例提升
- 中后期单位步数收益明显改善

新增失败判据：

- 只要 `1000` 步完成局占比明显下降，就判定当前 Phase C 改动失败
- 只要 `mode=charge` 失败局明显增多，就判定当前 Phase C 改动失败
- 只要高分局增加但均值完成度下降，也判定为失败，而不是“部分成功”

### 5.6 基于当前日志的最小实施版

原先判断“Phase B 已基本站住，因此可以直接推进最小 Phase C”的结论需要修正。

基于当前最新训练结果，现状更接近：

- 最近连续多局可稳定完成 `1000` 步
- 最近高分局普遍具备 `2~3` 次 charger arrival
- 但仍然存在 `mode=charge` 的提前失败局
- 说明 Phase C 相关策略已经开始对 Phase B 形成拖累

因此下一步不应直接继续推进原版 Phase C，而应改成 **Phase C 收缩版 / 受控版**：

1. **先保护 Phase B，不再默认扩大 Phase C**
   - 暂停继续增强“中后期偏 dirt”和“末段充电机会成本”
   - 先确认当前早死局是否与这些项的权重过强有关

2. **把 Phase C 改成 gated activation，而不是全局常开**
   - 只有在 `finished_steps=1000` 占比稳定、且 charge fail 不上升时，才允许逐步放大 Phase C
   - 对应到实现上，应优先做“满足条件才启用”的门控，而不是继续提高固定权重

3. **优先做 Phase C 的减伤改造，而不是增益改造**
   - 先减少它对充电安全和完成度的副作用
   - 再去追求 `900+` 局占比提升

### 5.7 修正后的 Phase C 实施原则

后续 Phase C 必须遵守以下原则：

1. **先灰度，再放量**
   - 任何提分项都先以弱权重、小门槛上线
   - 观察是否拖累完成度，再决定是否放大

2. **先门控，再加权**
   - 优先增加“何时允许启用”的条件
   - 不优先增加“启用后权重有多强”

3. **先保 charge 安全，再谈 score harvesting**
   - 只要回充安全边际不足，立即退回 Phase B 逻辑
   - `dirt harvesting` 不得覆盖生存策略

4. **先减副作用，再追高分**
   - 当前最优先问题不是高分不够，而是提分项正在拖累稳定性
   - 因此优化方向应是“把 Phase C 做得更不伤 B”，而不是“把 Phase C 做得更强”

### 5.8 下一版建议改法

下一版不建议直接追加新的 Phase C 奖惩项，而建议按下面顺序优化：

1. **给 Phase C 增加显式启用门槛**
   - 例如必须同时满足：已知充电桩、`charger slack` 充足、当前不在回充风险区、局面已进入明确中后期

2. **把 `dirt` 倾向做成软切换**
   - 不是突然压低 `frontier`
   - 而是随安全余量、脏区密度、剩余步数缓慢变化

3. **把“无收益步惩罚”改成上下文惩罚**
   - 对回充、找桩、脱困路径减弱惩罚
   - 只对真正的空转和回摆加强惩罚

4. **把高电量充电惩罚改成分段惩罚**
   - 在安全区内才施加机会成本
   - 临近风险区时快速衰减，避免误伤必要充电

### 5.9 直接对应代码的实施清单

为了避免后续继续停留在抽象描述，下一版建议直接按下面四个代码入口实施。

#### 5.9.1 `code/agent_ppo/algorithm/algorithm.py::_select_coverage_target`

这里负责决定当前局面更偏 `frontier` 还是更偏 `dirt`，因此是 Phase C 最容易拖累 Phase B 的入口。

建议改法：

1. 增加 `phase_c_enabled` 判定，而不是默认在全局评分里持续放大 `dirt`
2. `phase_c_enabled` 至少同时依赖以下条件：
   - 已知充电桩
   - `charger_slack` 高于安全阈值
   - 当前不处于 `should_charge=True`
   - 当前步数已经进入明确中后期
   - 局部或候选区域的 `dirt_gain` 足够高
3. 若不满足上述条件，则保持更接近 Phase B 的保守目标选择，不要主动压低 `frontier`
4. 对 `dirt` 权重提升改成软提升：
   - 由 `step_ratio`
   - `charger_slack`
   - `dirt_gain / info_gain`
   三项共同控制，而不是简单常数加权

建议新增的判断变量：

- `phase_c_gate_step_ratio`
- `phase_c_gate_charger_slack`
- `phase_c_gate_dirty_density`
- `phase_c_gate_should_charge`

#### 5.9.2 `code/agent_ppo/algorithm/algorithm.py::_rank_legal_actions`

这里决定局部一步动作评分，如果这个阶段把“提分导向”加得太猛，很容易把正常回充路径也打成低价值动作。

建议改法：

1. 对“向 `target_pos` 前进”的奖励保留，但在 `should_charge=True` 时优先保证回充路径对齐奖励
2. 仅当 `phase_c_enabled=True` 时，才对 `DIRT` 格子或 `frontier -> dirt` 转换做额外加权
3. 增加上下文减伤：
   - 若当前在回充模式，不施加 Phase C 的额外 `dirt` 偏置
   - 若当前刚完成 arrival 或处于找桩阶段，不施加过强的无效步机会成本
4. 若 `charger_slack` 低于阈值，则动作排序直接退回 Phase B 风格

重点不是“让高分动作更高”，而是：

- **避免高分导向动作去挤占安全动作的排序空间**

#### 5.9.3 `code/agent_ppo/feature/preprocessor.py::reward_process`

这里是当前 Phase C 副作用最容易扩散的地方，因为：

- `无收益步惩罚`
- `高电量充电惩罚`
- `回充相关惩罚`

都集中在这一层。

建议改法：

1. 把 `无清扫 + 无新观测` 惩罚改成“上下文化惩罚”
   - 若 `current_mode == "charge"`，减弱惩罚
   - 若 `should_charge == True`，减弱惩罚
   - 若刚确认 arrival、正在离开 charger 区域、或正在进行安全转场，减弱惩罚
2. 把 `charge_event_reward` 改成分段门控：
   - 高电量且远离风险区，才允许明显惩罚“过早充电”
   - 只要已进入回充风险区，机会成本应快速衰减到接近 0
3. 保留 `charge_loop_penalty`，但不要把正常回充停留过早放大为失败信号
4. 对 `unarrived_charger_progress_reward` 保持 Phase B 优先级：
   - 找桩收益和安全回充收益始终高于激进提分收益

建议新增的上下文变量：

- `phase_c_reward_enabled`
- `safe_charge_window`
- `charge_risk_zone`
- `transition_after_arrival`

#### 5.9.4 `code/agent_ppo/workflow/train_workflow.py`

这里不一定要直接改训练逻辑，但建议增加 **Phase C 回退监控**，否则后面很难快速判断“提分是否拖累完成度”。

建议改法：

1. 在现有监控项基础上，按固定窗口观察：
   - `finished_steps=1000` 占比
   - `mode=charge` 失败局占比
   - `charge_fail_after_arrival`
   - `arrival_confirmed_count`
   - `900+` 局占比
2. 若出现以下任一情况，则判定当前 Phase C 权重应回退：
   - `1000` 步局占比连续回落
   - `mode=charge` 失败局上升
   - `charge_fail_after_arrival` 上升
3. 文档层面明确要求：
   - 不必一开始就做自动回退
   - 但至少先把“回退判据”监控完整打出来

### 5.10 下一版推荐参数策略

下一版推荐采用“先门控、后放量”的参数策略，而不是继续直接改大奖惩幅度。

建议顺序：

1. **先加门控，不加大权重**
   - 先让 Phase C 只在安全条件满足时生效
   - 暂不继续放大 `dirt` 偏置和充电机会成本

2. **门控稳定后，再微调权重**
   - 先小幅提升 `dirt` 倾向
   - 再小幅增强中后期无收益步惩罚
   - 最后才碰高电量充电惩罚

3. **每次只改一类**
   - 一次只改 planner gate
   - 或一次只改 reward gate
   - 不要同一轮同时修改 target 选择和 reward 惩罚强度

### 5.11 下一版验收标准

下一版不再以“是否出现更多 `900+`”作为第一验收标准，而改成两级验收。

第一级：Phase B 保护是否成立

1. `1000` 步完成局占比不下降
2. `mode=charge` 失败局不增加
3. `charge_fail_after_arrival` 不增加
4. 满步局均分不明显回退

第二级：Phase C 是否真正有效

1. `900+` 局占比提升
2. `score / finished_steps` 提升
3. 中后期无收益步占比下降
4. 末段低性价比充电减少

只有第一级先通过，第二级才有意义。

这版修正后的实施仍保留三个边界：

- 不新增特征维度
- 不修改模型结构
- 不触碰保存逻辑、容器配置、`modelpool`、导出链路

建议只改两个实际训练文件：

- `code/agent_ppo/algorithm/algorithm.py`
- `code/agent_ppo/feature/preprocessor.py`

## 6. 明确不建议的方向

### 6.1 不要同时大改性能、奖励、特征和 planner

go24 的关键是分阶段验证。一次混改太多，后续无法判断收益来自哪里。

### 6.2 不要继续堆复杂 arrival gating

go23 在这部分已经有较高复杂度。go24 更适合：

- 先清理状态
- 再放宽误杀
- 最后看是否还需要细化

而不是继续增加更多阶段、更多回滚条件。

### 6.3 暂不碰保存与导出链路

沿用 `go24-3` 的边界约束：

- 不处理模型保存逻辑
- 不处理 `backup_model / user_ckpt_dir / model_file_save`
- 不处理 `modelpool`
- 不处理 docker / env 导出链路

## 7. 推荐实施顺序

### 第一步：先做 Phase A

只改 `preprocessor` 的 reset 与 episode 清理逻辑，确认性能问题是否主要来自跨局累积。

### 第二步：再做 Phase B 的最小闭环

建议先只做三项：

1. arrival 基础奖励适度增强
2. charge loop 判定放宽到“长时间无进展”才处罚
3. 提前结束改成额外惩罚，而不是额外奖励

这三项最直接对应“少早死、稳充电、保完成度”。

### 第三步：Phase B 验证通过后，再进入受控版 Phase C

优先顺序建议：

1. 先做 Phase C 启用门槛与回退机制
2. 再做温和版 score harvesting
3. 再做上下文化的无效步压缩
4. 最后才做充电机会成本建模

### 第四步：一旦拖累 Phase B，立即回退到“先修副作用”

明确规则：

1. 若完成度回退，优先削弱 Phase C，而不是继续补更多 Phase C 奖惩
2. 若 `charge` 失败局增多，优先恢复 Phase B 的保守约束
3. 若高分提升但稳定性下降，不视为可接受结果

## 8. 最终版 go24 成功标准

### 必须满足

1. 训练速度不再随局数明显恶化。
2. 大多数局稳定完成 `1000` 步。
3. 提前结束局显著下降。
4. 平均有效得分率不低于当前基线。
5. Phase C 的引入不能重新恶化 Phase B 指标。

### 期望满足

1. 训练速度和波动都优于 go23。
2. 完成度与平均分同步提升。
3. `900+` 高分局占比上升。
4. 中后期步数利用率更高，低效充电减少。
5. Phase C 与 Phase B 不再互相打架，而是形成受控叠加。

## 9. 总结

go24 的整合结论很明确：

- `go24-1` 负责解决 **性能累积下降**
- `go24-2/4` 负责解决 **提前结束与充电策略不稳**
- `go24-3` 负责在稳定跑满后进一步做 **受控提分优化**

因此最终不建议把四份文档并列执行，而应整合为一条分阶段路线：

- **A：先稳性能**
- **B：再稳完成度**
- **C：最后在不伤完成度的前提下提均分**

这条路线的优点是：

- 优先级清晰
- 风险可控
- 每阶段都有独立验证指标
- 更适合后续逐版迭代和归因
