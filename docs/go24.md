# go24：后续优化整合方案

## 1. 目标定义

go24 不再拆成彼此孤立的多版思路，而是整合为一条连续优化路线，按下面顺序推进：

1. 先解决 **性能随局数累积下降** 的问题，恢复稳定训练速度。
2. 再解决 **提前结束、充电失败、完成度不足** 的问题，保证大多数局能稳定跑满 `1000` 步。
3. 在生存与完成度基本稳定后，把重点切到 **平均有效得分率提升**，压缩无效步数，提高中后期收分效率。

一句话概括：

- **go24 是“先稳性能，再稳生存，最后提均分”的统一优化方案。**

---

## 2. 四份文档的整合结论

### 2.1 `go24-1` 的有效结论

`go24-1` 提供了最明确的问题指向：

- 当前主要性能问题不是单帧算力不足，而是 **跨局状态累积未清理**
- 根因高度集中在 `preprocessor.reset()` 没有完整清掉 go23 新增状态
- 优先级最高的是 **完整 reset + episode 结束显式清理**

这个方向应作为 go24 的 **Phase A**，且优先于任何策略调参。

### 2.2 `go24-2` 与 `go24-4` 的整合结论

`go24-2` 和 `go24-4` 基本是同一类方案，核心共识是：

- 当前低分局的重要来源是 **charge 阶段失败导致提前结束**
- arrival reward 偏弱、charge loop 判定偏严，可能让策略“不敢充”或“充得不稳定”
- 后续需要围绕 **完成度、充电时机、充电安全性** 做策略修正

这部分应作为 go24 的 **Phase B**。

但有一条需要修正：

- 原文里的 `completion_bonus` 实际写法是“提前结束反而加正奖励”，这会削弱 fail 惩罚，不适合作为默认主方案。
- 整合后应改成 **completion penalty / early termination penalty**，即：越早结束，终局惩罚越重，而不是越轻。

### 2.3 `go24-3` 的有效结论

`go24-3` 的判断成立，但前提是：

- 只有当大多数局已经能稳定打满 `1000` 步，优化重点才应该从“活下来”切到“提分”

因此 `go24-3` 不应和前两阶段并行混做，而应作为 **Phase C**：

- 聚焦中后期 score harvesting
- 压缩无效步数
- 建模充电机会成本

## 3. go24 总体路线图

## Phase A：性能稳定化

### 3.1 目标

解决训练过程中 6.9~16.1 步/秒的大幅波动，重点消除跨局累积导致的后期变慢。

### 3.2 核心判断

最可能根因是 go23 引入的状态结构没有在 episode reset 时完整清理，包括但不限于：

- `charger_regions`
- `rewarded_arrived_charger_regions`
- `charger_arrival_steps`
- `confirmed_charger_arrival_steps`
- `pending_arrivals`
- `candidate_charger_arrival_steps`
- `retro_canceled_arrivals`

### 3.3 必做项

1. 在 `code/agent_ppo/feature/preprocessor.py` 的 `reset()` 中完整清理 go23 新增局内状态。
2. 在 episode 结束逻辑里对 `pending_arrivals` 做显式 `.clear()`，避免残留引用。
3. 重置所有与 arrival/charge 统计有关的计数器，避免跨局污染。

### 3.4 可选项

1. 为 charger 区域增加快速查询缓存，如 `_charger_pos_set`。
2. 对 `_resolve_pending_arrivals()` 增加活跃项过滤，减少每帧无效遍历。
3. 必要时增加低频的数据结构重建，但这项优先级最低，只有在前两项完成后仍有性能问题才考虑。

### 3.5 验证指标

- 平均训练速度
- 最慢局速度
- 速度标准差
- 连续多局训练后是否仍出现明显降速趋势

### 3.6 成功标准

- 平均速度恢复到稳定区间
- 最慢局不再明显掉到 `7` 步/秒附近
- 性能波动显著收敛

---

## Phase B：完成度与充电策略稳定化

### 4.1 目标

在性能稳定后，优先解决：

- 提前结束
- charge 相关失败
- 低完成度导致的低分局

目标不是先追求高分，而是先把大多数局稳定推到 `1000` 步。

### 4.2 问题判断

综合 `go24-2/4`，当前问题大概率集中在三类：

1. `arrival reward` 太弱，策略对“安全抵达充电桩”的学习信号不足。
2. `charge loop` 判定过于激进，正常充电行为可能被误判为循环。
3. 到达充电桩后的后续收益判定过严，导致 arrival credit 容易回收或失真。

### 4.3 推荐主改动

#### 4.3.1 调整 arrival 基础奖励

可以提高 `_arrival_base_reward()` 的基础值，但要保持克制，建议：

- 第 1 个新桩：中等增强
- 第 2 个新桩：保留明显衰减
- 第 3 个及以后：只保留弱激励

原则是：

- 让策略愿意去找可用充电资源
- 但不能把“找桩”学成压倒清扫收益的主目标

#### 4.3.2 重写 charge loop 判定

不要再用过小阈值把正常进出 charger 区域判成失败。更合理的 loop 判定应同时考虑：

- 在 charge 阶段持续无新观测
- 持续无清扫收益
- 持续无法脱离局部困境
- 重复回访次数过多

也就是说，只有“长时间无进展”的充电过程才应视为 loop failure。

#### 4.3.3 放宽 arrival 后续确认的极端约束

需要检查 `_resolve_pending_arrivals()` 中这些条件是否过严：

- `coverage_gain`
- `observed_gain`
- `left_region`
- 过长确认窗口里的多次取消逻辑

建议方向：

- 保留 gating，但减少“正常可用 arrival 也被取消”的概率
- 让 step-level credit 更稳定，不要频繁回滚

#### 4.3.4 引入完成度惩罚，而不是完成度奖励

整合后明确采用：

- **越早结束，终局惩罚越强**
- **打满 `1000` 步不额外奖励，只视为基准**

建议终局设计思路：

- 完整局：保持现有 win/fail 终局框架
- 提前结束局：按 `finished_steps / 1000` 追加惩罚项

这样能避免“早死但少亏”的错误激励。

### 4.4 可选改动

1. 增加 `battery trend` 特征，帮助策略判断电量变化方向。
2. 为 planner 增加“当前桩过于危险，应该切换桩”的辅助信号。
3. 只在终局补少量 arrival quality bonus，奖励“找到多个桩且活到后期”的轨迹。

### 4.5 验证指标

- `finished_steps = 1000` 的局占比
- 提前结束局的平均得分
- charge 阶段失败次数
- 平均首次充电步数
- 平均充电次数

### 4.6 成功标准

- 大多数局能稳定跑满 `1000` 步
- 提前结束局显著减少
- 完成度提升的同时，平均分不回退
- 不引入新的明显性能损失

## Phase C：平均有效得分率提升

### 5.1 启动前提

只有当 Phase B 达成后，才建议进入这一阶段。判断标准是：

- 完成度已经稳定
- 早死已不再是主矛盾
- 主要差异变成“同样 `1000` 步，为什么有人 `900+`，有人 `700~800`”

### 5.2 目标

把更多步数从：

- 探索过度
- 回摆
- 低效绕行
- 低性价比充电

转成：

- 连续清扫
- 中后期高价值得分
- 更高的 `score / finished_steps`

### 5.3 三条主线

#### 5.3.1 中后期从 frontier 转向 score harvesting

思路是分阶段切换策略重心：

- 前期：扩图、找桩、建立路线
- 中期：扩图与清扫平衡
- 后期：优先兑现已知高价值脏区

建议改法：

1. 中后期提高 `dirt` 目标相对权重。
2. 剩余步数下降后，下调低收益 `frontier` 吸引力。
3. 当已知脏区密度足够高时，优先连续收分而不是继续远探。

#### 5.3.2 压缩无效步数

重点打击：

- `无清扫 + 无新观测`
- 小回环
- 高频 revisit
- 长时间停留在低收益区域

建议改法：

1. 强化连续无收益步惩罚。
2. 对短周期小回环做更平滑、连续的惩罚。
3. 对高 revisit 区域增加中后期机会成本。

#### 5.3.3 充电机会成本建模

后续要从“会不会充”升级为“这次充电值不值”。

建议加入：

1. 高电量时的过早充电惩罚。
2. 充电后若没有带来后续收益，则降低这次充电的奖励价值。
3. 末段剩余步数较少时，降低非必要充电倾向。

### 5.4 验证指标

- 平均 `score`
- 平均 `score / finished_steps`
- `900+` 局占比
- `500` 步后每 `100` 步得分
- `700~1000` 步区间清扫增量
- 无收益步数占比

### 5.5 成功标准

- 在完成度不下降前提下，平均有效得分率持续上升
- `900+` 高分局比例提升
- 中后期单位步数收益明显改善

### 5.6 基于当前日志的最小实施版

基于当前最新训练结果，Phase B 已基本站住：

- 最近连续多局可稳定完成 `1000` 步
- 最近高分局普遍具备 `2~3` 次 charger arrival
- 当前主问题已不再是“早死”，而是“如何把更多满步局从 `800+` 推到 `900+`”

因此下一刀不再扩展 Phase B，而是只做一版 **Phase C 最小改动**：

1. **planner 中后期偏向 `dirt`**
   - 当局面已经进入中后期时，降低纯 frontier 的吸引力
   - 同时提高已知 dirty 区域和高 `dirt_gain` 候选点的权重
   - 目标是减少“还能继续扩图，但不值”的远探

2. **reward 中后期压缩无收益步**
   - 对 `无清扫 + 无新观测` 的步数，在中后期增加额外惩罚
   - 目标是压缩回摆、低效绕行、站在低收益区域空转

3. **reward 末段抑制低性价比充电**
   - 对高电量、且没有清扫/观测收益的 charge 行为增加机会成本惩罚
   - 目标不是削弱必要充电，而是减少“能活但不划算”的补电

这版最小实施有三个明确边界：

- 不新增特征维度
- 不修改模型结构
- 不触碰保存逻辑、容器配置、`modelpool`、导出链路

建议只改两个实际训练文件：

- `code/agent_ppo/algorithm/algorithm.py`
- `code/agent_ppo/feature/preprocessor.py`

## 6. 明确不建议的方向

### 6.1 不要同时大改性能、奖励、特征和 planner

go24 的关键是分阶段验证。一次混改太多，后续无法判断收益来自哪里。

### 6.2 不要继续堆复杂 arrival gating

go23 在这部分已经有较高复杂度。go24 更适合：

- 先清理状态
- 再放宽误杀
- 最后看是否还需要细化

而不是继续增加更多阶段、更多回滚条件。

### 6.3 暂不碰保存与导出链路

沿用 `go24-3` 的边界约束：

- 不处理模型保存逻辑
- 不处理 `backup_model / user_ckpt_dir / model_file_save`
- 不处理 `modelpool`
- 不处理 docker / env 导出链路

---

## 7. 推荐实施顺序

### 第一步：先做 Phase A

只改 `preprocessor` 的 reset 与 episode 清理逻辑，确认性能问题是否主要来自跨局累积。

### 第二步：再做 Phase B 的最小闭环

建议先只做三项：

1. arrival 基础奖励适度增强
2. charge loop 判定放宽到“长时间无进展”才处罚
3. 提前结束改成额外惩罚，而不是额外奖励

这三项最直接对应“少早死、稳充电、保完成度”。

### 第三步：Phase B 验证通过后，再进入 Phase C

优先顺序建议：

1. 中后期 score harvesting
2. 无效步数压缩
3. 充电机会成本建模

---

## 8. 最终版 go24 成功标准

### 必须满足

1. 训练速度不再随局数明显恶化。
2. 大多数局稳定完成 `1000` 步。
3. 提前结束局显著下降。
4. 平均有效得分率不低于当前基线。

### 期望满足

1. 训练速度和波动都优于 go23。
2. 完成度与平均分同步提升。
3. `900+` 高分局占比上升。
4. 中后期步数利用率更高，低效充电减少。

---

## 9. 总结

go24 的整合结论很明确：

- `go24-1` 负责解决 **性能累积下降**
- `go24-2/4` 负责解决 **提前结束与充电策略不稳**
- `go24-3` 负责在稳定跑满后进一步做 **提分优化**

因此最终不建议把四份文档并列执行，而应整合为一条分阶段路线：

- **A：先稳性能**
- **B：再稳完成度**
- **C：最后提均分**

这条路线的优点是：

- 优先级清晰
- 风险可控
- 每阶段都有独立验证指标
- 更适合后续逐版迭代和归因
